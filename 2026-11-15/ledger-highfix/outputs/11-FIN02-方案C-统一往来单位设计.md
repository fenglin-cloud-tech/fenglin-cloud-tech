## 一、主数据归属

**结论：新建平台级主数据服务 `fenglin-mdm-service`，独立库 `fenglin_mdm`（schema `fenglin_mdm`），由平台侧维护，业务域可“提交”但不直接改主数据。**

- 表：`mdm_business_partner`
  - `id` 雪花 ID（对外一律字符串）
  - `tenant_id`、`partner_code`（租户内唯一，规则 `BP` + 6 位序列）
  - `name`、`short_name`、`unified_credit_code`、`legal_rep`、`contact_*`
  - `partner_type`：`CUSTOMER` / `SUPPLIER` / `BOTH`
  - `status`：`DRAFT` / `ENABLED` / `DISABLED` / `MERGED`
  - `source_domain` + `source_ref`：首次收编来源（crm/finance/service/legal），用于幂等与追溯
  - `normalized_name`、`dedup_key`、`merged_into`
  - 标准审计列（created/updated/deleted/version）
- 维护权：
  - 平台管理员：新增、合并、停用、改统一社会信用代码
  - 业务域：通过 `POST /api/mdm/v1/partners:propose` 提交候选，平台审核入库；紧急录单场景走“降级本地临时单位”，恢复后归并
  - 不接受业务域直接 `PUT` 主数据，避免四域各改一份
- 去重与合并（“XX公司” vs “XX有限公司”）：
  1. 统一社会信用代码相同 → 直接判定同一单位
  2. 归一化名称相同 → 同一单位。归一化：去首尾空白、全半角统一、去掉括号内容、去除“有限责任公司/有限公司/股份有限公司/集团/公司”等后缀、去标点
  3. 归一化后编辑距离 / 公共前缀达到阈值 → 进入“疑似重复”队列，由平台人工合并，不自动合并
  4. 合并动作：保留主记录 ID，被合并记录置 `MERGED` 并写 `merged_into`，引用方 ID 批量改写；合并可重放、有操作日志

## 二、四域引用方式

统一模式：**业务库只存 `partner_id` + 名称快照，列表不回源；选择器与详情按需调用 MDM；本地缓存兜底。**

| 域 | 现有本地字段 | 过渡方式 | 读取方式 | 成本 |
| --- | --- | --- | --- | --- |
| 云销 CRM 客户 | `crm_customer.*` | 增加 `partner_id`，名称/信用代码保留 | 选择器调 MDM；列表读本地快照 + Caffeine 缓存（TTL 10 分钟） | 低：1 列 + 1 个选择器改造 |
| 云财 供应商 | 无主数据表，仅 `fin_payable.supplier_id/name` | 新增 `partner_id` 到应付/付款；供应商维护页改为 MDM 入口 | 同上 | 中：ARAP 4 处选择器 + 3 张单据表加列 |
| 云财 应收/收款 | `customer_id/customer_name` 快照 | 增加 `partner_id`，名称快照保留 | 选择器调 MDM（客户类型），列表只读快照 | 中 |
| 云服 工单客户 | 工单表客户字段 | 增加 `partner_id` | 选择器调 MDM | 低：1 列 + 1 选择器 |
| 云法 合同相对方 | 合同相对方文本/ID | 增加 `partner_id`，文本保留 | 选择器调 MDM | 低：1 列 + 1 选择器 |

**不选共享库直读**：跨服务共享库会绕开 MDM 的合并/权限/审计，后续无法收敛；统一走 API + 本地缓存，读多写少，缓存命中后列表页无额外 RT。

## 三、数据迁移

1. 建表与索引（`tenant_id + normalized_name`、`tenant_id + unified_credit_code`、`tenant_id + source_domain + source_ref` 唯一）
2. 收编顺序：CRM 客户 → 财务供应商（从 ARAP 往来名称去重生成）→ 云服客户 → 云法相对方
3. 匹配规则：信用代码精确 → 归一化名称精确 → 新建；命中疑似重复只入队不合并
4. 脚本幂等：以 `(tenant_id, source_domain, source_ref)` 唯一键 upsert；重复执行只更新 `updated_at`
5. 先 dry-run：输出“将新建/将复用/疑似重复”三张清单，人工确认后再写
6. 回滚：
   - 业务侧只新增 `partner_id` 列，旧列不动；功能开关关闭即回到现状
   - `partner_id` 列可整列删除，不影响既有单据
   - MDM 库可整库回滚（迁移前快照），失败不触碰业务库
7. 近义名：不自动合并；合并只由平台人工触发，保留 `merged_into` 追溯

## 四、兼容期

- 旧字段**全部保留**：`customer_id/customer_name`、`supplier_id/supplier_name`、合同相对方文本
- 过渡期**双写**：新建/修改单据同时写 `partner_id` 与旧字段；名称一律写快照
- 读取策略：页面展示优先快照（不远程 JOIN），选择器展示 MDM 实时结果
- 一致性校验：每日任务比对“`partner_id` 对应名称 vs 快照名称”，差异出报表，不自动改数
- 收尾条件（同时满足才可停双写）：
  1. 四域选择器全部切到 MDM
  2. 连续 30 天名称差异 = 0、`partner_id` 空值率 = 0（历史单据除外）
  3. 合并队列清零
- 收尾动作：停止写旧 ID、保留名称快照与旧列只读；旧列删除另立清理单，不在本期

## 五、降级（硬要求）

- 触发条件：MDM 不可用、超时、HTTP 非 2xx、业务码非 0
- 具体取值：连接超时 2s、读取超时 3s（总 5s）；失败重试 1 次（间隔 200ms）；连续 5 次失败熔断 60s
- 降级行为（各域一致）：
  - 录单**不阻断**：允许手填单位名称；能拿到缓存 ID 就存 `partner_id`，拿不到则 `partner_id` 为空、只存名称快照
  - 标记：单据写 `partner_verified=false` + `partner_verify_note`（如“主数据服务不可用，未校验”），并写审计事件
  - 页面明确提示“未校验”，不得伪装成已匹配
- 对账：MDM 恢复后跑“未校验单据”清单，按归一化名称给出候选，人工确认后回填 `partner_id`；**不自动覆盖用户填写值**
- 允许程度：客户/供应商/工单客户/合同相对方均可降级录单；主数据的新增、合并、停用不可降级（只能稍后补做）

## 六、影响面

- 新增服务：`fenglin-mdm-service`（端口、网关路由 `/api/mdm/v1`、内网鉴权）
- 改造服务：hub（权限码与租户初始化）、CRM、finance、service、legal、admin-ui、developer-portal（对外接口的单位字段）
- 表：新增 MDM 2~3 张表；CRM/财务（应付、付款、应收、收款）/工单/合同各加 `partner_id` 及校验标记列
- 页面：4 个选择器、4 个列表名称回显、平台主数据管理页（新增/合并/停用/疑似重复队列）
- 停机窗口：**不需要**。全部为加列、加服务、加开关；收编在低峰执行
- 与已完成工作冲突评估：
  - FIN-01/04/05/08/11/12/13：不冲突；FIN-02 只改 ARAP 选择器与名称回显，不动已修页面结构
  - CRM-09 回调：回调里若带客户信息，需增加 `partner_id` 透传，属增量字段
  - OPEN-08：对外接口的单位标识需明确“对外仍用业务 ID，MDM ID 仅内部使用”，避免破坏外部契约；需在开放平台文档补映射说明
  - FIN-15 租户开通：MDM 初始化需纳入开通编排（或提供幂等初始化接口），否则新租户无主数据

## 七、分期建议（每步完成后系统可用）

1. **P0 地基**：MDM 服务 + 表 + 读写 API + 平台管理页 + 权限码；不改任何业务域。系统行为不变。
2. **P1 云销客户**：CRM 加 `partner_id`、选择器切 MDM、列表读快照；开启双写与校验任务。
3. **P2 云财**：应收/应付/收款/付款四处选择器统一；供应商维护迁到 MDM；落降级与“未校验”标记（此步完成即满足本次降级硬要求）。
4. **P3 云服 + 云法**：工单客户、合同相对方接 `partner_id`。
5. **P4 收敛**：停双写、清空合并队列、旧列转只读；删除旧列另立清理单。

每期均有独立回滚开关；P2 结束前，FIN-02 在台账保持开放（架构待定→实施中），不提前标记已修复。
