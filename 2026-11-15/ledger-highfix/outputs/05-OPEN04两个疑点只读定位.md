## 一、审核意见乱码：仅造数工具问题，入库链路无缺陷

### 1.1 判据一：明确正确编码的新请求回读完好

新造 APP2026000012（`enc-probe-create.json` / `enc-probe-reject.json` / `enc-probe-detail-after.json`）：

- 请求体文件 `body-utf8-probe-reject.json` 为 UTF-8（`curl --data-binary` 原样发送，不经 PowerShell 字符串中转）。
- 审核返回 200；详情回读：`review_comment = 中文编码校验：驳回原因应完整回显，不允许乱码`，`reviewed_at` 正常。
- 库内校验：该行 `review_comment` 字符数 22、UTF-8 66 字节，MD5 为 `3b57f6fb83391bfaa752a0899ff7aac9`，与 Python 对该正确字符串按 UTF-8 计算的 MD5 完全一致。
- 同轮另一条正确样例 APP2026000010（“缺少生产回调域名白名单说明，请补充后重新提交”）MD5 `fad0af364fa3f709367c52f2016593e4`，亦一致。

结论：只要请求字节是正确 UTF-8，服务端解析、落库、回读全链路不会破坏中文。

**0008/0009 的根因已复现到字节级**（`enc-probe-b64.txt` + `enc-probe-ps-read.txt` + 请求体原文件）：

- 最强证据：当时 `curl --data-binary` 实际发出的请求体 `ev-r.json` / `ev-ap.json`（已归档为 `enc-probe-src-ev-r.json` / `enc-probe-src-ev-ap.json`），其 reason 字节与库内 0009 / 0008 **逐字节完全相同** —— 服务端收到的就已经是乱码。
- 两个脚本文件本身是 UTF-8（无 BOM），但 `powershell.exe` 5.1 执行 `.ps1` 时按系统 ANSI（CP936）解码，中文字面量被读成 `缂哄皯鐢熶骇…` 这类字符；
- 用 ANSI 等价解码（GB18030，CP936 超集）读取脚本、提取 `$bodyR`/`$bodyAp` 的 reason 后按 UTF-8 重算 MD5，与库内完全一致：
  - `0037f29d9a445c0ed46f1c1d0482da9c`（33 字符 / 98 B）＝ 库内 0009；
  - `8b60309833ecc84d367f154baa4fb89b`（27 字符 / 81 B）＝ 库内 0008；
- 即：**请求发出前内容已被改写，服务端只是如实存储收到的字节**。

**0004/0005 的根因**：请求体文件即由带损编码（ASCII）写出，中文全部变成 `?`（0x3F），证据为 `enc-probe-src-open04-reject.json` / `enc-probe-src-open04-approve.json` 的十六进制。

### 1.4 结论

**仅造数工具问题**（PowerShell 5.1 按 ANSI 读取 UTF-8 脚本 / ASCII 落盘），入库链路无缺陷。
可选加固（非缺陷，未做）：服务端对 `?` 占比异常或 U+FFFD 做告警；造数统一走 UTF-8 文件 + `curl --data-binary`。

## 二、驳回后重新提交：缺陷（需求要求可重提，实现无该流转）

### 2.1 代码中的实际状态机

| 动作 | 前置 | 结果 | 依据 |
| --- | --- | --- | --- |
| 创建（管理端 1001 / 门户等价） | 同租户名称唯一 | `review_status=PENDING`、`status=DISABLED` | `OpenAppMapper.insert`、`OpenAppService.create` |
| 审核 1002 | **仅 `review_status='PENDING'`**（SQL `... AND review_status='PENDING'`） | APPROVE → `APPROVED/ENABLED`；REJECT → `REJECTED/DISABLED` | `OpenAppMapper.updateReview`、`OpenAppService.review` |
| 再次审核 | 非 PENDING | 条件更新 0 行 → **409**「应用当前状态不可审核」 | `OpenAppService.review` L99-103 |
| 门户改回调/订阅 | 仅校验 owner，无审核状态限制 | 可改，但不改状态 | `updateCallback` / `updateScopes` |
| 重新提交 | — | **无接口、无 UI、无状态迁移** | `OpenApiPortalController` 仅 1006/1001/详情/回调/scopes/密钥/沙箱/日志/配额 |
| 同名重建 | — | `findByTenantAndName` 不过滤审核状态 → **409 应用已存在** | `OpenAppMapper.findByTenantAndName` |

即：`PENDING` 是唯一入审入口，`APPROVED/REJECTED` 为终态；驳回后既不能重提，也不能用同名重建（只能改名重建）。你们看到的 409 是这条约束的直接表现，不是偶发错误。

### 2.2 契约/需求依据

| 文档 | 表述 | 指向 |
| --- | --- | --- |
| 《00_丰麟云枢_12_系统管理员手册》L387 | “开放应用审核不通过｜查看驳回意见，**完善 scope/回调/安全措施后重提**” | 明确要求可重提 |
| 《00_丰麟云枢_01_项目需求规格说明书》FR-HUB-OPEN-006 | “应用上架审核流程（提交→审核→上架/驳回）” | 审核闭环含驳回 |
| 《00_丰麟云枢_02_架构设计文档》4.3 | “任一驳回：返回发起人 → 记录意见 → **可重新提交**（新实例，幂等键隔离）” | 通用审批要求（非应用专用，但方向一致） |
| 《00_丰麟云枢_05_接口文档》HUB-API-1001~1006 | 定义了创建/审核/详情/列表等，**未定义重提 API** | 契约缺口 |

### 2.3 结论

**缺陷**：需求/运维手册承诺“驳回后可完善再重提”，但接口契约未定义、代码无流转、门户无入口，且同名重建被名称唯一校验挡住。不是“有意设计”。

若要修（待裁决，未改代码），最小闭环建议：

1. 新增 `POST /openapi/portal/apps/{id}:resubmit`：仅 owner + `review_status='REJECTED'` 可调用；条件更新为 `PENDING/DISABLED`，写审计 `OPENAPI_APP_RESUBMITTED`；重复提交 409。
2. 保留还是清空最近一次驳回意见需产品定：建议**保留** `review_comment/reviewed_at` 供开发者对照，新一轮审核覆盖。
3. 管理端 1002 审核无需改动（回到 PENDING 即可审核）；门户 REJECTED 详情增加「修改后重新提交」按钮，先允许改回调/scopes。
4. 契约补 HUB-API-1007（或 1001 扩展）并写明 1002 前置为 PENDING；若最终定为“驳回=作废重建”，则需同步改管理员手册与页面提示，并放开同名重建或明确“改名重建”。
