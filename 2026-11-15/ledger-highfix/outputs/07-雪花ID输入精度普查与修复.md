# 雪花 ID 输入精度普查与修复（PLAT-36，2026-11-15）

> 触发：OPEN-08 回归时发现管理端「应用审核」手输 app_id 被 `el-input-number` 收成 JS number，19 位雪花 ID 末 4 位被改写。
> 范围：全仓 `el-input-number` 逐条分类；ID 类改文本输入，金额类单列核查。
> 规程：真实浏览器验证、请求原文对照、提交不推送。

## 一、方法

1. 全仓检索 `el-input-number`（`frontend/**`）：共 **135 行命中**，其中 2 行为样式文件/样式块（`design-lab/vendor/element-plus.css`、`LegalConfigView.vue` 样式），实际控件 **133 处 / 53 个文件**。
2. 逐条读取绑定字段与提交路径，判定为：**ID / 金额 / 数量 / 其它数值**。
3. ID 类统一替换为共享组件 `IdInput`（`frontend/packages/ui-admin/src/components/IdInput.vue`）：`el-input` + `inputmode=numeric` + 输入时剔除非数字 + `maxlength=19`，**始终以字符串承载，不做 Number 转换**；对应表单字段 TS 类型由 `number` 收敛为 `string`。后端 `Long` 接受 JSON 字符串，无需改后端。
4. 金额类核查后端接收类型与是否用整型接分。
5. 改动页面用真实浏览器输入 19 位 ID 提交，抓请求原文比对。

## 四、金额专项结论：未发现精度缺陷，不做改动

- 后端接收入参全部为 `BigDecimal`（CRM：`CrmDtos` 中 `amount`/`unitPrice`/`annualRevenue`/`arr`/`taxRate`/`discountRate`；财务：`FinanceDtos` 中金额字段），**全仓主代码未发现 `long/int` 接“分”的金额字段**（`grep` 到的 long amount 仅在测试辅助方法）。
- 前端 `el-input-number` 两位小数场景：JSON 序列化走最短往返表示（如 `1234.56` → `"1234.56"`），不会出现 `1234.5599999`；金额量级远小于 2^53，未观察到截断。
- 唯一“未设 `:precision`”的是 `portal-ui/MyOpportunitiesView.stageForm.amount`（以及后台商机金额），可输入多位小数，但后端 `BigDecimal` 原样接收，属业务校验范畴，不改控件类型。
- 结论：金额类保持 `el-input-number`；如后续引入“分”整型契约，再单独评估。

## 五、真实精度截断案例

- **已发生的真实案例**：2026-11-15 17:24，管理端「开放平台 → 应用审核」输入 `2121896408260186114`，提交时 `el-input-number` 存成 `2121896408260186000`，请求发往不存在的应用（当时表现为 404/无效审核）。见 `outputs/06-OPEN08驳回后重提实现与回归.md` 第五节“已知遗留”。
- **可复现步骤（修复前控件）**：任意绑定 `el-input-number` 的 ID 输入框输入 19 位 ID → 失焦 → 页面回显即以 `...186000` 结尾 → 提交抓包路径/请求体同样是截断值。
- **机制复现**：`Number('2121896408260186114') === 2121896408260186000`（> 2^53，末 4 位不可表示）。
- 修复后同一输入不再转换，页面与请求均为原值（见第六节）。
