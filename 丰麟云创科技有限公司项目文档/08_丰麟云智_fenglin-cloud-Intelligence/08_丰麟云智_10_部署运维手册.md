## 2 部署拓扑

### 2.1 standalone 模式拓扑

```
Internet → WAF/CDN → fenglin-gateway（3副本）
                        │ 暴露：/api/intelligence/v1/**、/app/**、/admin/**、/openapi/**
                        ▼
        fenglin-intelligence-service（6副本，HPA）
          ├── PostgreSQL（主从）  ├── Redis Cluster
          ├── Elasticsearch集群   ├── Milvus集群
          ├── ClickHouse集群      ├── Kafka集群
          └── MinIO集群
                        ▼
        LLM/Embedding/Rerank（公有云 API + 本地 vLLM 兜底）
```

### 2.2 embedded 模式拓扑

```
7 款宿主产品（云销/云协/云才/云财/云研/云服/云法）
        │ 内网 mTLS + 服务令牌（X-Caller-Product/X-On-Behalf-Of）
        ▼
fenglin-gateway（内网实例）
  仅放行 /internal/** 与内部化 /api/intelligence/v1/**；门户路由拒绝
        ▼
fenglin-intelligence-service（intelligence.mode=embedded）
  能力授权（ai_capability_grant）→ 计量（ai_usage_metering）
        ▼
  共享 PG/Redis/ES/Milvus/ClickHouse（tenant_id+host_product 隔离）
```

### 2.3 双模式部署差异

| 项 | standalone | embedded |
|---|---|---|
| 网关暴露 | 门户+业务+开放 | 仅 `/internal/**`（+内部化 API） |
| 门户 Ingress | 启用 | 禁用（无 `/app`、`/admin` Ingress） |
| 配置 | `intelligence.mode=standalone` | `intelligence.mode=embedded` |
| 计费 | 独立席位/调用量 | 计量计入宿主 |
| 鉴权 | 用户 JWT | mTLS+服务令牌+用户代理头 |

## 4 部署步骤

### 4.1 前置准备

1. 创建命名空间：`kubectl create ns fenglin-intelligence`；
2. 配置 Secret：数据库口令、Redis 口令、KMS 访问凭据、模型 Key（经 KMS，不落 Git）；
3. 初始化中间件（PG/ES/Milvus/CH/Redis/Kafka/MinIO）并验证连通；
4. 在 Nacos 导入 `fenglin-intelligence-{env}.yaml`。

### 4.2 数据库迁移

```bash
# 使用 Flyway 执行迁移（生产环境经发布流水线审批）
flyway -url=jdbc:postgresql://pg-primary:5432/fenglin_intelligence \
       -user=fenglin_ai -password=${DB_PWD} \
       -locations=filesystem:./db/migration migrate
# 校验脚本与 RLS
psql -h pg-primary -U fenglin_ai -d fenglin_intelligence -c "\dP ai_document"
```

### 4.3 应用部署（Kubernetes）

```yaml
# deployment.yaml（节选）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: fenglin-intelligence-service
  namespace: fenglin-intelligence
spec:
  replicas: 6
  selector:
    matchLabels: { app: fenglin-intelligence-service }
  template:
    metadata:
      labels: { app: fenglin-intelligence-service }
    spec:
      containers:
      - name: app
        image: registry.fenglincloud.com/fenglin/fenglin-intelligence-service:1.0.0
        ports: [ { containerPort: 8080 } ]
        env:
        - name: INTELLIGENCE_MODE      # 双模式：standalone | embedded
          valueFrom: { configMapKeyRef: { name: ai-mode, key: intelligence.mode } }
        - name: SPRING_PROFILES_ACTIVE
          value: prod
        readinessProbe: { httpGet: { path: /actuator/health/readiness, port: 8080 }, initialDelaySeconds: 30 }
        livenessProbe:  { httpGet: { path: /actuator/health/liveness, port: 8080 }, initialDelaySeconds: 60 }
        resources: { requests: { cpu: "4", memory: "8Gi" }, limits: { cpu: "16", memory: "32Gi" } }
```

```bash
# 应用部署
kubectl apply -f k8s/configmap.yaml
kubectl apply -f k8s/secret.yaml     # 由密钥管理注入
kubectl apply -f k8s/deployment.yaml
kubectl apply -f k8s/service.yaml
kubectl apply -f k8s/ingress.yaml    # standalone 才包含门户 ingress
kubectl rollout status deploy/fenglin-intelligence-service -n fenglin-intelligence
```

### 4.4 双模式部署要点

```bash
# ① 独立产品模式
kubectl -n fenglin-intelligence create configmap ai-mode \
  --from-literal=intelligence.mode=standalone
# 应用门户 Ingress（/app/intelligence、/admin/intelligence、/api/intelligence/v1）

# ② 能力嵌入模式
kubectl -n fenglin-intelligence create configmap ai-mode \
  --from-literal=intelligence.mode=embedded
# 不部署门户 Ingress；网关仅放行 /internal/**；配置 7 个宿主产品的服务证书与能力授权
kubectl apply -f k8s/internal-ingress.yaml
```

### 4.5 初始化数据

```bash
# 初始化字典、默认提示词、默认指标模板（Flyway V1_0_16）
# 创建默认知识库、默认模型供应商（Key 经 KMS）
curl -X POST https://intelligence.fenglincloud.com/api/intelligence/v1/admin/knowledge-bases \
  -H "Authorization: Bearer ${ADMIN_TOKEN}" -H "X-Tenant-Id: 10001" -H "X-Client-Type: ADMIN" \
  -d '{"name":"默认知识库","scopeType":"TENANT","defaultSecLevel":2,"embeddingModel":"bge-large-zh"}'
```

## 5 配置清单

### 5.1 核心配置（`fenglin-intelligence-{env}.yaml`）

| 配置项 | 默认 | 说明 |
|---|---|---|
| `intelligence.mode` | `standalone` | **双模式开关**（standalone/embedded） |
| `intelligence.portal.enabled` | `true` | standalone 门户路由 |
| `intelligence.internal.enabled` | `false` | embedded 内部契约 |
| `intelligence.search.fulltext-weight` | `0.4` | 混合检索全文权重 |
| `intelligence.search.vector-weight` | `0.6` | 混合检索向量权重 |
| `intelligence.search.top-k` | `20` | 召回 Top-K |
| `intelligence.search.rerank-top-n` | `10` | 重排返回数 |
| `intelligence.search.rerank.enabled` | `true` | 重排开关 |
| `intelligence.rag.context-max-tokens` | `8000` | 上下文窗口 |
| `intelligence.rag.only-kb` | `false` | 仅依据知识库 |
| `intelligence.llm.default-provider` | `llm-public-a` | 默认模型 |
| `intelligence.llm.ttft-timeout-ms` | `2000` | 首字超时 |
| `intelligence.llm.fallback.enabled` | `true` | 降级 |
| `intelligence.guardrail.input.prompt-injection` | `BLOCK` | 注入拦截 |
| `intelligence.guardrail.output.pii-masking` | `MASK` | PII 脱敏 |
| `intelligence.bi.mode` | `ACCELERATE` | 大屏默认抽取 |
| `intelligence.bi.query-timeout-ms` | `15000` | 查询超时 |
| `intelligence.bi.row-limit` | `100000` | 行数上限 |
| `intelligence.metering.enabled` | `true` | 计量开关 |
| `intelligence.embedding.model` | `bge-large-zh` | 嵌入模型 |
| `intelligence.vector.dimension` | `1024` | 向量维度 |

### 5.2 敏感配置

- 数据库/Redis/Kafka 口令、KMS 凭据、模型 Key：一律由 K8s Secret + KMS 注入，禁止写入 Git 与配置中心明文；
- 启动校验：若 `intelligence.mode` 与暴露面配置不一致（如 standalone 却关闭门户），启动失败并告警。

## 6 灰度与回滚

### 6.1 灰度

1. **模型灰度**：新提示词/新模型按租户或流量比例灰度（`routing_weight`/版本开关）；
2. **应用灰度**：ArgoCD 分批次滚动（25%→50%→100%），观察检索 P95、TTFT、错误率、护栏命中；
3. **能力灰度**（embedded）：按宿主产品逐个开启能力授权，验证后放量；
4. **索引模型升级**：双写迁移（新嵌入模型建新集合，灰度检索对比，达标后切换）。

### 6.2 回滚

```bash
# 应用回滚（GitOps 回退到上一 Revision）
argocd app rollback fenglin-intelligence  --revision <PREV>
# 或
kubectl -n fenglin-intelligence rollout undo deploy/fenglin-intelligence-service

# 配置回滚（模式/权重/护栏）
# 修改 Nacos 配置后推送，或回退 ConfigMap 版本
kubectl -n fenglin-intelligence rollout restart deploy/fenglin-intelligence-service

# 提示词/Agent 回滚
POST /api/intelligence/v1/admin/prompts/{code}/versions/{ver}:publish  # 发布旧版本即回滚
```

**回滚判据**：检索 P95 > 400ms 持续 5min、TTFT P95 > 3s、错误率 > 0.5%、越权/安全告警触发。

## 7 监控告警

### 7.1 监控指标

| 类别 | 指标 | 阈值/告警 |
|---|---|---|
| 检索 | QPS、P95/P99、缓存命中率、零结果率 | P95 > 260ms 预警；> 400ms 告警 |
| LLM | TTFT、TPOT、成功率、降级次数 | TTFT P95 > 2s 告警 |
| 索引 | 任务积压、失败率、吞吐 token/min | 积压 > 1 万 或 失败率 > 2% |
| BI | 看板 P95、CH 慢查询、连接数 | P95 > 1.5s 告警 |
| 向量 | 查询延迟、CPU、集合大小 | CPU > 85% 告警 |
| 资源 | CPU/内存/GC/磁盘/网络 | 标准阈值 |
| 业务 | 审核积压、洞察任务成功率、计量延迟 | 洞察成功率 < 99% |
| 安全 | 护栏命中、越权拦截、异常登录 | 越权拦截激增告警 |
| 双模式 | 模式一致性、能力授权拒绝率、计量丢失率 | 计量丢失 > 0 告警 |

### 7.2 告警通道

Prometheus + Alertmanager → 企业微信/飞书/邮件/短信；分等级（P0 电话+P1 群+P2 邮件）。

### 7.3 关键看板

- 检索健康大盘（QPS/P95/命中/零结果）；
- LLM 网关大盘（TTFT/TPOT/供应商/降级）；
- 索引流水线大盘（吞吐/积压/失败）；
- BI 性能大盘（看板/CH 慢查询）；
- 双模式计量与授权大盘。

## 8 备份恢复

| 对象 | 备份策略 | 恢复目标 |
|---|---|---|
| PostgreSQL | 每日全备 + WAL 归档（PITR），异地副本 | RPO ≤ 5min，RTO ≤ 30min |
| Elasticsearch | 快照（每日）+ 索引可重建 | RPO ≤ 24h，可全量重建 |
| Milvus | 集合快照 + 可从分块重新嵌入 | 可重建 |
| ClickHouse | 分片副本 + 每日备份 | RPO ≤ 24h |
| MinIO | 版本化 + 异地复制 | RPO ≤ 15min |
| Redis | RDB+AOF | 缓存可重建 |
| 配置中心 | Nacos 配置版本化 | 秒级 |

**恢复演练**：季度执行 1 次（数据库 PITR、索引重建、CH 恢复），记录 RPO/RTO 实测值。

**索引重建**：当 ES/向量库不可恢复时，以 PG `ai_document_chunk` 为权威源，重新执行嵌入与索引（500 万文档约 13 小时，10 节点）。

## 9 巡检与应急预案

### 9.1 日常巡检（每日）

| 项 | 检查 |
|---|---|
| 服务健康 | 各副本就绪、无 CrashLoop、无 5xx 激增 |
| 检索 | QPS/P95/零结果率正常 |
| LLM | TTFT/成功率/配额余量 |
| 索引 | 积压与失败率、最近任务状态 |
| BI | CH 慢查询、看板 P95 |
| 计量 | 计量延迟与丢失率 0 |
| 安全 | 护栏命中、越权拦截、审计留存 |
| 存储 | 磁盘/对象存储水位 < 80% |
| 备份 | 备份任务成功 |

### 9.2 巡检周/月

- 周：相关性抽检（NDCG）、引用准确率抽检、洞察准确率抽检；
- 月：容量趋势、成本分析、密钥轮换检查、权限复核、漏洞扫描。

### 9.3 应急预案

| 事件 | 处置 |
|---|---|
| 检索延迟飙升 | 检查 ES/Milvus 负载 → 扩容/降级（关闭重排/缩 Top-K）→ 启用缓存 |
| LLM 不可用 | 切换备用供应商 → 启用本地 vLLM → 降级为仅检索 |
| 向量库故障 | 降级为全文检索（standalone 提示、embedded 返回 degraded）→ 修复后重建 |
| 索引积压 | 提升 XXL-Job 并发/优先级 → 扩容嵌入实例 |
| BI 大屏超时 | 切抽取模式 → CH 预聚合 → 限流 |
| 越权/安全告警 | 立即封禁可疑主体 → 审计追溯 → 复核权限配置 → 上报安全组 |
| 数据库主库故障 | Patroni 自动切换 → 验证读写 → 根因分析 |
| 计量异常 | 对账核查 → 幂等补偿 → 修正账单 |
| 双模式配置漂移 | 执行一致性校验 → 回滚配置 → 重启校验 |

### 9.4 值班与升级

- P0（服务不可用/数据泄漏/越权）：15 分钟响应，立即升级至产品负责人+安全组；
- P1（核心功能降级）：30 分钟响应，2 小时恢复；
- P2/P3：工作日处理。
