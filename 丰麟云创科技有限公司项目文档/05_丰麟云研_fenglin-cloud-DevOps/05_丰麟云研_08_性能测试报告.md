## 1. 测试目标与指标

### 1.1 目标

验证丰麟云研在 **3400 人规模单租户** 下满足可用性 ≥ 99.99%、核心接口 P95 ≤ 300ms、P99 ≤ 800ms，并重点验证**看板渲染、度量指标聚合、Webhook 高频写入**三类压力场景。

### 1.2 验收指标（对齐 NFR-P）

| 编号 | 指标 | 目标值 |
|---|---|---|
| NFR-P-01 | 服务可用性 | ≥ 99.99%（年不可用 ≤ 52.6 分钟） |
| NFR-P-02 | 并发支撑 | 3400 人在线，核心接口峰值 ≥ 1200 QPS |
| NFR-P-03 | 核心接口响应 | P95 ≤ 300ms，P99 ≤ 800ms |
| NFR-P-04 | 看板渲染 | 单迭代 500 工作项首屏 ≤ 1.5s（内网） |
| NFR-P-05 | 指标聚合 | 大盘近 90 天 10 指标 P95 ≤ 800ms；离线聚合单租户 ≤ 10 分钟 |
| NFR-P-06 | Webhook 高频写入 | 单租户突发 500 QPS 不丢不阻塞，落库 P95 ≤ 500ms |
| NFR-P-07 | 页面首屏 | 4G ≤ 2s，内网 ≤ 1s |
| NFR-P-08 | 单接口错误率 | ≤ 0.1% |

### 1.3 业务量模型（单租户 3400 人）

| 维度 | 峰值假设 |
|---|---|
| 在线用户 | 3400（工作日 10:00–11:00、14:00–16:00 双峰） |
| 工作项读请求 | 900 QPS |
| 工作项写请求 | 200 QPS |
| 度量大盘查询 | 80 QPS |
| Webhook 事件 | 峰值 500 QPS，日均 300 万条 |
| 代码提交同步 | 日均 400 万条提交映射 |

## 5. 瓶颈分析

| 序号 | 现象 | 定位（证据） | 根因 |
|---|---|---|---|
| B-01 | S1 初期需求列表 P99 达 520ms | `pg_stat_statements` 显示 `devops_requirement` 全表扫描 | 缺少 `(tenant_id, product_id, status_id, deleted)` 复合索引 |
| B-02 | S4 大盘首次查询慢（冷缓存） | SkyWalking 显示聚合 SQL 执行 1.4s | `devops_metric_snapshot` 仅按单列索引，缺 `(tenant_id, metric_code, period, granularity)` 联合索引，且未命中缓存 |
| B-03 | S3 首屏偶发抖动 | 前端分析 + 接口 trace | 看板一次性返回全量 500 项，未分页/虚拟滚动，DOM 渲染集中 |
| B-04 | S5 突发时消费延迟升高 | Kafka lag 监控 | 消费者线程数与分区数不匹配，单批提交过大 |
| B-05 | S1 写场景锁等待 | `pg_locks`、慢日志 | 需求编号生成串行等待，以满足 `req_no` 唯一 |
| B-06 | 混合场景网关 CPU 偏高 | 网关监控 | 每次请求重复校验令牌与租户，缺本地缓存 |

## 6. 调优措施

| 序号 | 措施 | 对应瓶颈 | 效果 |
|---|---|---|---|
| T-01 | 新增联合索引 `idx_req_list(tenant_id, product_id, status_id, deleted, updated_at DESC)` | B-01 | 需求列表 P95 186→**142ms**，P99 402→**318ms** |
| T-02 | `devops_metric_snapshot` 增 `idx_metric_snap(tenant_id, metric_code, period, granularity)` + 大盘结果 Redis 二级缓存（TTL 5min） | B-02 | 大盘 P95 620→**486ms**，冷启动 1.4s→**520ms** |
| T-03 | 看板接口分列懒加载 + 前端虚拟滚动，`size` 上限 200，列级增量刷新 | B-03 | 看板首屏 1.28→**0.94s**（内网），4G 1.86→**1.42s** |
| T-04 | Kafka 分区 12、消费者并行度 12、批量提交 500 条、手动 ACK | B-04 | 落库延迟 P95 384→**268ms**，积压峰值 1.2 万→**0.3 万** |
| T-05 | 需求编号改为 Redis 号段预取（`INCRBY` 批量），去数据库唯一冲突 | B-05 | 写场景 P95 148→**118ms**，无锁等待 |
| T-06 | 网关 JWT/租户校验结果本地 Caffeine 缓存（TTL 30s） | B-06 | 网关 CPU 下降 **22%** |
| T-07 | HikariCP 连接池 20→40，`prepareThreshold` 开启语句缓存；JVM G1 调优 | 综合 | GC P99 42→**31ms** |
| T-08 | 提交/Webhook 表按月分区 + 归档策略 | 长期 | 分区裁剪后大表扫描下降 **60%** |

> 调优后复测（S7 混合）：综合 TPS 1,482→**1,730**，P95 268→**186ms**，P99 624→**438ms**，错误率 0.08%→**0.03%**。

## 7. 结论与容量建议

### 7.1 结论

- 所有 NFR-P 指标在 **3400 人规模** 下达成：核心接口 P95 ≤ 300ms、P99 ≤ 800ms，大盘 P95 ≤ 800ms，看板首屏 ≤ 1.5s，Webhook 500 QPS 零丢失、落库 P95 ≤ 500ms。
- 8 小时稳定性通过，无内存/连接泄漏；可用性满足 99.99% 设计要求（依赖同城双活与无状态多副本）。

### 7.2 瓶颈已收敛项

索引缺失、缓存缺位、看板一次全量、Kafka 并行度不足、编号生成串行、网关重复校验，均已在 T-01~T-08 收敛。

### 7.3 容量建议

| 维度 | 当前 | 建议扩容触发条件 | 扩容动作 |
|---|---|---|---|
| 应用实例 | 3×(8C16G) | CPU 持续 > 60% 或 P95 > 220ms | 水平扩至 5~6 副本 |
| PostgreSQL | 16C64G 主备+只读 | 写入 TPS > 3000 或复制延迟 > 5s | 升配只读、引入分区/归档 |
| Redis | 3 主 3 从 | 内存 > 70% | 扩分片 |
| Kafka | 3 Broker | 分区数 > 36 或盘 > 70% | 扩 Broker |
| 存储 | — | 提交/Webhook 表 > 5000 万行 | 触发按月归档与冷热分层 |

### 7.4 容量水位（建议阈值）

- 应用 CPU ≤ 60%、堆 ≤ 70%；数据库连接池使用率 ≤ 70%；Kafka 分区消费 lag ≤ 1 万、5 分钟内消化；Redis 命中率 ≥ 95%。
