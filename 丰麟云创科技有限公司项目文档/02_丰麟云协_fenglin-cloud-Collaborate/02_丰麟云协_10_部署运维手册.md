## 2. 部署拓扑

```
                        Internet
                           │
                    [DDoS/WAF/LB]
                           │
                 ┌─────────┴─────────┐
                 │  fenglin-gateway  │  (鉴权/限流/路由/灰度)
                 └─────────┬─────────┘
          ┌────────────────┼────────────────┐
          │                │                │
  [collab-portal-ui]  [collab-service]  [WebSocket 网关]
  [collab-admin-ui]    (4~12 副本)        (IM/文档长连接)
          │                │                │
          └────────┬───────┴───────┬────────┘
                   │               │
        ┌──────────┼───────────────┼──────────┬──────────┐
        │          │               │          │          │
  [PostgreSQL]  [Redis]        [Kafka]  [Elasticsearch] [MinIO]
   1主2从       3主3从         3Broker    3节点          4节点
        │
   [异地容灾只读副本]
```

- 同城双活：应用区跨 3 可用区；数据层主从跨可用区。
- 异地容灾：PostgreSQL 异步复制至异地只读副本；MinIO 跨区复制。
- 灰度：网关按用户/租户标签分流至 new/old 版本。

## 4. 部署步骤

### 4.1 前置准备

1. 命名空间与配额：`kubectl create ns fenglin-collab`；设置 ResourceQuota 与 LimitRange。
2. Nacos 配置导入：`fenglin-collab-prod.yaml`（见第 5 章）。
3. 密钥注入：KMS/Secret（数据库口令、JWT 公钥、MinIO AK/SK、Kafka SASL）。
4. 数据库初始化：执行 Flyway 迁移（见 4.3）。

### 4.2 容器镜像构建与推送

```bash
# 后端
mvn -pl fenglin-collab-service clean package -DskipTests
docker build -t registry.fenglincloud.com/fenglin/fenglin-collab-service:1.0.0 .
docker push registry.fenglincloud.com/fenglin/fenglin-collab-service:1.0.0

# 前端（用户端/管理端）
pnpm --filter fenglin-collab-portal-ui build
pnpm --filter fenglin-collab-admin-ui build
docker build -t registry.fenglincloud.com/fenglin/fenglin-collab-portal-ui:1.0.0 .
docker push registry.fenglincloud.com/fenglin/fenglin-collab-portal-ui:1.0.0
```

### 4.3 数据库迁移（Flyway）

```bash
# 迁移脚本目录：db/migration
# V1.0.0 脚本：
#   V1_0_0__init_collab_schema.sql        (32 张 collab_ 表)
#   V1_0_1__init_collab_index_rls.sql     (索引 + 行级安全策略)
#   V1_0_2__encrypt_collab_pii.sql        (手机号等 PII 加密 + phone_hash)
#   V1_0_3__seed_collab_dict.sql          (字典与模板种子)

# 执行迁移（应用启动自动执行亦可）
java -jar fenglin-collab-service.jar --spring.flyway.enabled=true --spring.flyway.baseline-on-migrate=false
```

> 强制约束：所有数据库结构变更必须通过 Flyway 脚本，禁止手工改表；生产迁移前须在 STAGING 验证并备份。

### 4.4 应用部署（GitOps / ArgoCD）

```bash
# ArgoCD 同步（推荐）
argocd app sync fenglin-collab-prod

# 或 kubectl 应用清单
kubectl apply -f k8s/collab-service-deploy.yaml -n fenglin-collab
kubectl apply -f k8s/collab-ws-deploy.yaml -n fenglin-collab
kubectl apply -f k8s/collab-portal-deploy.yaml -n fenglin-collab
kubectl apply -f k8s/collab-admin-deploy.yaml -n fenglin-collab
kubectl apply -f k8s/collab-hpa.yaml -n fenglin-collab
```

### 4.5 部署后校验

```bash
# 就绪与健康
kubectl -n fenglin-collab get pods
curl -s https://collab.fenglincloud.com/actuator/health   # {"status":"UP"}

# 冒烟：登录 → 发送消息 → 创建工作台卡片
curl -s -X POST https://collab.fenglincloud.com/api/collab/v1/im/messages \
  -H "Authorization: Bearer $TOKEN" -H "X-Tenant-Id: 1" -H "X-Client-Type: PORTAL" \
  -H "Idempotency-Key: smoke-001" -d '{"conversationId":"1","content":"smoke","type":"TEXT"}'
```

验收项：Pod 全部 Running/Ready；健康检查 UP；冒烟通过；监控面板无红色告警。

## 5. 配置清单

### 5.1 应用配置（`fenglin-collab-prod.yaml`）

```yaml
spring:
  application:
    name: fenglin-collab-service
  datasource:
    url: jdbc:postgresql://pg-collab-prod:5432/fenglin_collab
    hikari:
      # 池大小按 §5.1「连接池容量推导」计算后由部署环境注入；旧值 50 / 10 已失效
      maximum-pool-size: ${DB_POOL_MAX}
      # 必须显式设置：Hikari 未配置时默认等于 maximum-pool-size，启动即占满池配额
      minimum-idle: ${DB_POOL_MIN_IDLE}
      connection-timeout: 3000
  data:
    redis:
      cluster:
        nodes: redis-collab-prod-0:6379,redis-collab-prod-1:6379,redis-collab-prod-2:6379
  kafka:
    bootstrap-servers: kafka-prod-0:9092,kafka-prod-1:9092,kafka-prod-2:9092
    producer:
      acks: all
      retries: 3
    consumer:
      group-id: fenglin-collab

collab:
  im:
    max-message-length: 8000          # 单条消息最大字符
    send-rate-limit-per-sec: 20       # 单用户每秒发送上限
    message-retention-days: 1095      # 消息留存 3 年
    recall-window-minutes: 1440       # 撤回窗口 24h
  doc:
    max-doc-size-mb: 20
    collab-max-users: 50              # 单文档协同上限
    snapshot-interval-secs: 30
    watermark-enabled: true
  meeting:
    booking-lock-timeout-ms: 3000
    room-open-hours: "08:00-22:00"
  ona:
    data-window-days: 90
    anonymity-threshold: 5            # 部门人数 < 5 不出图
    snapshot-cron: "0 0 2 * * ?"
  approval:
    engine: flowable
    task-timeout-hours: 48
  security:
    pii-encrypt: AES-256-GCM
    tenant-isolation: enforced
    audit-retention-months: 12
```

> **连接池容量推导（替代固定建议值）**
>
> - 单实例可分配上限 = `max_connections` − `superuser_reserved_connections`（默认 3）− 运维/监控/备份预留（建议 ≥ 10）。
> - 本服务池上限 = 单实例可分配上限 ÷ 连接同一数据库的服务实例数（同库其它服务 + 本服务副本数）。
> - `minimum-idle` 必须显式设置（建议为池上限的 1/4～1/2，且 ≥ 1）；Hikari 未配置时默认等于 `maximum-pool-size`，每个实例启动即预占满池配额。
> - 旧建议值 `maximum-pool-size: 50` / `minimum-idle: 10` 已失效：按单实例直连估算，未扣减运维/监控/备份预留，也未按同库实例数分摊。
> - 拓扑前提：本手册未记录生产 `max_connections`、同库服务实例数与副本数，属**待确认项**；单库与分库的算法不同，数值不得直接沿用旧值，上线前须按实际拓扑复核。

### 5.2 关键配置项说明

| 配置项 | 默认 | 说明 |
|---|---|---|
| `collab.im.send-rate-limit-per-sec` | 20 | 超限返回 2001006 |
| `collab.doc.collab-max-users` | 50 | 超限拒绝新协作会话 |
| `collab.meeting.booking-lock-timeout-ms` | 3000 | 预定锁超时 |
| `collab.ona.anonymity-threshold` | 5 | 隐私匿名阈值 |
| `collab.security.audit-retention-months` | 12 | 审计留存 |
| `collab.approval.task-timeout-hours` | 48 | 审批超时告警 |

配置变更流程：Nacos 修改 → 灰度环境验证 → 生产发布 → 记录变更单。

## 6. 灰度与回滚

### 6.1 灰度策略

| 阶段 | 流量 | 观察指标 | 时长 |
|---|---|---|---|
| 金丝雀 | 1 个 Pod（内部用户/1 个测试租户） | 错误率、P95、异常日志 | 30min |
| 小流量 | 5% 租户 | 上述 + 业务指标（消息成功率、协同同步率） | 2h |
| 半量 | 50% 租户 | 上述 + 资源使用 | 4h |
| 全量 | 100% | 全量监控 | — |

灰度分流由网关按租户/用户标签实现；新版本与旧版本共存，数据库迁移须向后兼容（禁止破坏性变更，先加列后删列跨版本）。

### 6.2 回滚方案

| 场景 | 操作 | 目标时间 |
|---|---|---|
| 应用异常 | ArgoCD 回滚至上个版本：`argocd app rollback fenglin-collab-prod` | ≤5min |
| 配置错误 | Nacos 回退配置并推送 | ≤3min |
| 数据库迁移问题 | 使用备份 PITR 恢复 + 回退应用版本 | ≤30min |
| 中间件故障 | 切换从库/副本，降级非核心功能（如关闭 ONA 实时分析） | ≤15min |

回滚后须：验证健康检查、冒烟、对账（消息条数、文档版本、审批实例）。

## 7. 监控告警

### 7.1 监控指标

| 层次 | 指标 | 来源 |
|---|---|---|
| 应用 | QPS、P95/P99、错误率、JVM 堆/GC、线程池 | Prometheus JMX |
| 业务 | 消息成功率、协同同步率、会议室超定数、审批时效 | 业务埋点 |
| 连接 | WebSocket 在线数、连接建立失败率 | WS 网关 |
| 中间件 | PG 连接/慢查询/IOPS、Redis 命中率、Kafka lag、ES 查询延迟 | Exporter |
| 网关 | 限流次数、路由错误率、灰度流量 | Gateway |
| 基础设施 | 节点 CPU/内存/磁盘/网络 | Node Exporter |
| 链路 | 全链路 Trace | SkyWalking |

### 7.2 告警规则（示例）

| 告警 | 条件 | 级别 | 处置 |
|---|---|---|---|
| 服务不可用 | 健康检查连续 3 次失败 | 紧急 | 摘除节点 + 扩容 + 通知 |
| 错误率超限 | 5min 错误率 > 1% | 紧急 | 排查 + 回滚预案 |
| P95 超限 | 5min P95 > 500ms | 严重 | 扩容 + 定位慢点 |
| Kafka Lag 高 | `collab.message` lag > 100,000 | 严重 | 扩分区/扩消费者 |
| PG 慢查询 | 慢查询 > 20/分钟 | 严重 | 索引优化 |
| Redis 内存高 | 使用率 > 85% | 严重 | 扩容/清理 |
| IM 发送失败率 | > 1% | 严重 | 检查 Kafka/WS |
| ONA 任务失败 | XXL-Job 任务失败 | 一般 | 重跑 |

告警通道：值班电话 + 企微/飞书群 + 邮件；分级升级机制（5min 未响应升级）。

## 8. 备份恢复

### 8.1 备份策略

| 对象 | 策略 | 保留 | 异地 |
|---|---|---|---|
| PostgreSQL | 每日 02:00 全备 + WAL 持续归档（PITR） | 全备 30 天，WAL 7 天 | 异地异步复制 |
| Redis | 每日 RDB + 实时 AOF | 7 天 | 否（可重建） |
| Kafka | 分区副本 3，retention 7 天 | 7 天 | 否 |
| ES | 每日快照至 MinIO | 14 天 | 是 |
| MinIO | 版本化 + 跨区复制 | 按桶生命周期 | 是 |
| 审计日志 | WORM 不可变存储 | 12 个月 | 是 |

### 8.2 恢复演练

- 频率：季度。
- 演练项：单表恢复、整库 PITR、MinIO 单文件恢复、ES 索引恢复。
- 实测（V1.0.0）：RPO = 8s，RTO = 42s，满足 RPO ≤ 5min / RTO ≤ 30min。
- 恢复流程：
  1. 申请恢复（变更单 + 安全评审）；
  2. 从备份/异地副本恢复至隔离环境；
  3. 数据校验（行数、校验和、业务对账）；
  4. 切流并观察。

## 9. 巡检与应急预案

### 9.1 日常巡检（每日/每周/每月）

| 周期 | 巡检项 |
|---|---|
| 每日 | Pod 状态、健康检查、告警清零、Kafka lag、PG 慢查询、备份成功、磁盘水位 |
| 每周 | 日志异常统计、连接池水位、Redis 命中率、证书有效期、容量趋势 |
| 每月 | 压测抽样、漏洞扫描、权限审计、备份恢复抽样、容量评估 |

### 9.2 应急预案

| 故障场景 | 现象 | 处置步骤 | 恢复目标 |
|---|---|---|---|
| IM 消息积压 | Kafka lag 飙升、消息延迟 | 扩消费并发/扩分区 → 检查下游 → 必要时限流非核心 | ≤15min |
| 文档协同不同步 | 协同同步率下降 | 检查 WS 网关 → 检查快照服务 → 重启异常 Pod | ≤15min |
| 数据库主库故障 | 写入失败 | 主从切换（Patroni）→ 校验数据 → 恢复主库 | RTO ≤ 30min |
| 会议室超定 | 数据异常 | 停写 → 冲突数据修正 → 唯一约束核对 → 恢复 | ≤30min |
| 审批流程阻塞 | 实例卡住 | 检查 Flowable 引擎 → 补偿/重试 → 人工干预 | ≤30min |
| 缓存雪崩 | 大量穿透 DB | 限流 → 缓存预热 → 热点隔离 | ≤20min |
| 安全事件 | 异常访问/泄露告警 | 隔离 → 取证 → 阻断 → 通知 → 复盘 | 立即响应 |

应急联系人（值班表）与升级路径见运维平台；重大事件按《安全事件应急预案》上报。

### 9.3 变更管理

- 所有生产变更须变更单；结构变更须 Flyway + STAGING 验证 + 备份。
- 变更窗口：业务低峰（22:00–06:00）；紧急变更须回滚预案。
- 变更后 30min 内加密监控值守。
