## 1 环境规划

### 1.1 环境矩阵

| 环境 | 用途 | 域名 | 命名空间 | 副本 | 数据库 |
|---|---|---|---|---|---|
| dev | 开发自测 | dev-crm.fenglincloud.com | `fenglin-crm-dev` | 1 | `fenglin_crm_dev` |
| test | 功能/集成测试 | test-crm.fenglincloud.com | `fenglin-crm-test` | 2 | `fenglin_crm_test` |
| staging | 预发/回归/压测 | staging-crm.fenglincloud.com | `fenglin-crm-staging` | 4 | `fenglin_crm_staging` |
| prod | 生产 | crm.fenglincloud.com | `fenglin-crm` | 8（弹性至 12） | `fenglin_crm` |

### 1.2 生产资源规格

| 组件 | 规格 | 数量 | 说明 |
|---|---|---|---|
| `fenglin-crm-service` | 8C16G（容器限 6C12G） | 8 | HPA：CPU>65% 扩容至 12 |
| `fenglin-gateway` | 4C8G | 2 | 双活 |
| PostgreSQL 15 | 16C64G + SSD | 1 主 + 2 从 | 流复制 + 读写分离 |
| Redis 7 | 8C16G | 3 主 3 从（Cluster） | 缓存/分布式锁/限流 |
| Kafka 3.6 | 8C16G | 3 Broker | 事件总线 |
| RocketMQ 5 | 8C16G | 2 主 2 从 | 事务消息（佣金/结算） |
| Elasticsearch 8 | 8C32G | 3 节点 | 检索 + IK 分词 |
| MinIO | 8C16G | 4 节点 | 附件/导出文件 |
| XXL-Job 2.4 | 4C8G | 2 | 调度（健康度重算/舆情采集） |
| Flowable 7（中台） | 4C8G | 2 | 审批流引擎 |
| Nacos 2.3 / Sentinel 1.8 | 4C8G | 各 2 | 注册配置/流控 |
| Prometheus+Grafana+Loki+SkyWalking | 8C16G | 各 2 | 可观测 |

### 1.3 网络与安全要求

- 生产环境 HTTPS（TLS 1.2+，推荐 1.3），证书由 KMS 签发与自动轮换；
- 数据库/中间件仅应用网段可达，管理端口禁公网；
- K8s NetworkPolicy 限定命名空间内互通；内部接口 `/internal/**` 仅 mTLS 服务间调用；
- 密钥/口令由 KMS + K8s Secret 管理，禁止硬编码。

## 4 部署步骤（容器/脚本）

### 4.1 构建与镜像

```bash
# 1) 构建后端
mvn -T 4 clean package -DskipTests -P prod
# 2) 构建镜像（多阶段，基础镜像最小化，非 root）
docker build -t registry.fenglincloud.com/crm/fenglin-crm-service:1.0.0 .

# 3) 前端
pnpm -C fenglin-hub-admin-ui install && pnpm -C fenglin-hub-admin-ui build   # /admin/crm
pnpm -C fenglin-hub-portal-ui install && pnpm -C fenglin-hub-portal-ui build  # /app/crm

# 4) 镜像签名 + 推送
cosign sign --key kms://crm-sign registry.fenglincloud.com/crm/fenglin-crm-service:1.0.0
docker push registry.fenglincloud.com/crm/fenglin-crm-service:1.0.0
```

### 4.2 数据库迁移（Flyway，强制）

```bash
# 迁移由发布流水线自动执行；禁止手工改库
flyway -url=jdbc:postgresql://pg-primary:5432/fenglin_crm \
       -user=crm_migrator -locations=filesystem:./db/migration \
       -baselineOnMigrate=false migrate
# 脚本：V1_0_1__init_crm_schema.sql ... V1_0_15__add_partition_jobs.sql
```

迁移顺序（与 FL-CRM-DB-003 第 8 章一致）：`V1_0_1` 基线建表 → `V1_0_2` 索引 → `V1_0_3` RLS 策略 → `V1_0_4` PII 加密列与 `{field}_hash` → … → `V1_0_15` 分区与归档任务。迁移前自动快照，失败自动回滚并阻断发布。

### 4.3 K8s 部署

```bash
# 1) 配置与密钥
kubectl -n fenglin-crm create secret generic crm-secret \
  --from-literal=DB_PASSWORD="$CRM_DB_PASSWORD" \
  --from-literal=REDIS_PASSWORD="$CRM_REDIS_PASSWORD" \
  --from-literal=KMS_KEY_ID="$CRM_KMS_KEY_ID" --dry-run=client -o yaml | kubectl apply -f -

# 2) 应用部署（ArgoCD GitOps 同步）
kubectl -n fenglin-crm apply -f k8s/deployment.yaml       # Deployment + HPA + PDB
kubectl -n fenglin-crm apply -f k8s/service.yaml          # ClusterIP + ServiceMonitor
kubectl -n fenglin-crm apply -f k8s/networkpolicy.yaml    # 网络策略
kubectl -n fenglin-crm apply -f k8s/ingress.yaml          # /api/crm/v1 路由

# 3) 校验
kubectl -n fenglin-crm rollout status deploy/fenglin-crm-service
kubectl -n fenglin-crm get pods -l app=fenglin-crm-service
curl -s https://crm.fenglincloud.com/actuator/health | jq .
```

`deployment.yaml` 关键片段：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: fenglin-crm-service, namespace: fenglin-crm }
spec:
  replicas: 8
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 2, maxUnavailable: 0 }
  template:
    spec:
      securityContext: { runAsNonRoot: true, runAsUser: 10001 }
      containers:
        - name: app
          image: registry.fenglincloud.com/crm/fenglin-crm-service:1.0.0
          resources:
            requests: { cpu: "2", memory: 4Gi }
            limits:   { cpu: "6", memory: 12Gi }
          readinessProbe: { httpGet: { path: /actuator/health/readiness, port: 8080 }, initialDelaySeconds: 30 }
          livenessProbe:  { httpGet: { path: /actuator/health/liveness,  port: 8080 }, initialDelaySeconds: 60 }
          envFrom: [{ secretRef: { name: crm-secret } }]
```

### 4.4 发布流水线（GitLab CI + ArgoCD）

```
commit → 单元测试 → SAST/SCA/镜像扫描 → 构建签名 → 推送仓库
      → 部署 staging → 集成/回归（TC 回归组 R1–R9）→ Flyway 迁移（prod 预检）
      → ArgoCD 灰度发布 prod → 观测窗口 → 全量
```

## 6 灰度与回滚

### 6.1 灰度策略（Argo Rollouts）

| 阶段 | 流量比例 | 观测窗口 | 通过条件 |
|---|---|---|---|
| 金丝雀 | 5% | 10min | 错误率 ≤0.1%，P95 ≤300ms，无异常日志 |
| 分批放量 | 30% → 50% | 各 10min | 同上且业务指标无异常（转化率/审批成功率） |
| 全量 | 100% | 30min 值守 | 同上 |

灰度按租户白名单 + 流量比例双维度；管理端配置类变更同步灰度；数据库迁移采用**向前兼容**策略（先加列后切换，禁止破坏性 DDL）。

### 6.2 回滚

```bash
# 应用回滚（Argo Rollouts）
kubectl argo rollouts undo deployment/fenglin-crm-service -n fenglin-crm

# 或指定版本
kubectl argo rollouts set image deployment/fenglin-crm-service \
  app=registry.fenglincloud.com/crm/fenglin-crm-service:0.9.9 -n fenglin-crm
```

触发回滚条件：错误率 >0.5% 持续 5min、P95 >500ms 持续 10min、S1 缺陷、数据异常。回滚 SLA ≤5 分钟；数据库回滚仅允许通过后续 Flyway 补偿脚本（不回退已执行脚本），并保留现场数据。

## 7 监控告警

### 7.1 监控指标

| 层面 | 指标 | 阈值/告警 |
|---|---|---|
| 应用 | QPS、P95/P99、错误率、JVM GC、线程池 | P95 >300ms 或错误率 >0.5% 告警 |
| 网关 | 请求量、限流次数、鉴权失败率 | 限流突增、401/403 异常升高告警 |
| 数据库 | CPU、连接数、慢查询、复制延迟 | CPU >75%、复制延迟 >30s 告警 |
| Redis | 命中率、内存、集群健康 | 命中率 <90%、内存 >80% 告警 |
| Kafka | 消费滞后、分区均衡 | 滞后 >10 万条告警 |
| ES | 集群状态、查询延迟 | 状态非 green、P95 >200ms 告警 |
| 任务 | 健康度重算成功率、采集成功率 | 成功率 <99%、超时告警 |
| 业务 | 线索转化、续费率、预警触达时延 | 预警触达 >5min、转化异常下降告警 |
| 可用性 | `/actuator/health`、合成拨测 | 不可用立即告警（P0） |

### 7.2 告警分级与通知

| 级别 | 场景 | 通知渠道 | 响应 |
|---|---|---|---|
| P0 | 服务不可用、数据异常、安全事件 | 电话 + 企微/飞书 + 邮件 | 5min 内响应 |
| P1 | 核心指标劣化、任务失败 | 企微/飞书 + 邮件 | 15min 内响应 |
| P2 | 非核心告警、容量预警 | 邮件 | 当日处理 |
| P3 | 巡检提示 | 工单 | 计划内处理 |

告警规则由 Prometheus + Alertmanager 定义，纳管于 Git（IaC）；告警须可抑制、可静默、可追溯到值班人。

## 8 备份恢复

### 8.1 备份策略

| 对象 | 策略 | 保留 |
|---|---|---|
| PostgreSQL | 每日全备 + 每 15min WAL 归档（PITR） | 全备 30 天、WAL 7 天 |
| 对象存储（MinIO） | 版本控制 + 每日增量 | 按生命周期 90 天 |
| ES 索引 | 每日快照到对象存储 | 30 天 |
| Redis | AOF + 每日 RDB | 7 天 |
| 配置（Nacos） | 每日导出 + Git 版本 | 永久 |
| K8s 资源 | GitOps 仓库版本化 | 永久 |

异地容灾：WAL 与全备异地异步复制；同城双活 + 异地备份，RPO ≤5min、RTO ≤30min（演练实测 RPO 2.4min / RTO 18min）。

### 8.2 恢复流程

```bash
# 1) 数据库 PITR 恢复
pg_basebackup -D /var/lib/pgsql/restore -h pg-backup
# 配置 recovery_target_time 后启动，按时间点恢复至故障前

# 2) 校验
psql -c "SELECT count(*) FROM crm_lead;"   # 关键表行数校验
# 3) 应用指向新实例并回归核心链路（TC 回归组 R1–R6）
```

恢复演练：每季度一次，覆盖误删数据、库故障、可用区故障三类场景；演练报告归档。

## 9 巡检与应急预案

### 9.1 巡检清单

| 频率 | 项目 |
|---|---|
| 每日 | 服务健康、告警清零、任务成功、备份完成、磁盘/容量水位 |
| 每周 | 慢查询 TOP、限流统计、预警触达时延、审计异常、安全告警 |
| 每月 | 容量趋势、依赖版本漏洞、密钥轮换状态、权限复核 |
| 每季度 | 容灾演练、恢复演练、压测基准回归、安全复评 |

巡检结果记录于运维台账；异常转工单并闭环。

### 9.2 应急预案

| 场景 | 现象 | 处置步骤 |
|---|---|---|
| 服务不可用 | health 失败、5xx 上升 | 1) 确认影响范围 2) 检查网关/依赖 3) 扩容或回滚 4) 恢复后回归 |
| 数据库故障 | 连接失败、复制中断 | 1) 主从切换（自动/手动）2) 校验数据一致性 3) 修复原主并重建复制 |
| 中间件异常 | Kafka 积压/Redis 抖动/ES 红 | 1) 降级（缓存击穿保护/检索降级）2) 扩容或重启 3) 补数据 |
| 审批任务堆积 | 流程超时升级增多 | 1) 扩容工作流实例 2) 检查节点路由 3) 人工兜底推进 |
| 健康度重算失败 | 任务失败/超时 | 1) 分片重试（幂等）2) 保留上次结果 3) 定位慢因子数据源 |
| 预警未触达 | 触达时延 >5min | 1) 检查消息链路 2) 重试队列补发 3) 人工通知责任人 |
| 安全事件 | 越权/异常访问 | 1) 隔离账号 2) 审计溯源 3) 加固 4) 按安全事件流程上报 |
| 误删数据 | 数据缺失 | 1) PITR 恢复至故障前 2) 校验 3) 回归核心链路 |

值班与升级：一线运维（7×24）→ 二线研发值班 → 三线架构/安全；P0 事件 15 分钟内成立应急小组，30 分钟内对外通报进展，事后 3 个工作日内提交复盘报告。
