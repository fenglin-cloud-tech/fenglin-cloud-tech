## 1 环境规划

### 1.1 环境矩阵

| 环境 | 用途 | 域名 | 命名空间 | 副本（api/worker） | 数据库 |
|---|---|---|---|---|---|
| dev | 开发自测 | dev-service.fenglincloud.com | `fenglin-service-dev` | 1 / 1 | `fenglin_service_dev` |
| test | 功能/集成测试 | test-service.fenglincloud.com | `fenglin-service-test` | 2 / 1 | `fenglin_service_test` |
| staging | 预发/回归/压测/安全 | staging-service.fenglincloud.com | `fenglin-service-staging` | 4 / 3 | `fenglin_service_staging` |
| prod | 生产 | service.fenglincloud.com | `fenglin-service` | 8 / 4 | `fenglin_service` |

### 1.2 生产资源规格

| 组件 | 规格 | 数量 | 说明 |
|---|---|---|---|
| `fenglin-service-service`(api) | 8C16G（容器限 6C12G） | 8 | HPA：CPU>65% 扩容至 12 |
| `fenglin-service-service`(worker) | 8C16G | 4 | 调度/异步/挖掘批处理 |
| `fenglin-service-service`(job-scheduler) | 4C8G | 1+1（主备） | XXL-Job 执行器 |
| `fenglin-service-rpa-agent` | 4C8G（客户侧） | 按机器人规模 | 独立网段部署 |
| `fenglin-gateway` | 4C8G | 2 | 双活 |
| PostgreSQL 15 | 16C64G + SSD | 1 主 + 2 从 | 流复制 + 读写分离 |
| Redis 7 | 8C16G | 3 主 3 从（Cluster） | 缓存/分布式锁/限流 |
| Kafka 3.6 | 8C16G | 3 Broker | 事件总线 |
| Elasticsearch 8 | 8C32G | 3 节点 | 检索（含 IK）+ 挖掘/知识 |
| MinIO | 8C16G | 4 节点 | 附件/截图/导出/导入报告 |
| XXL-Job 2.4 | 4C8G | 2 | 调度中心 |
| Flowable 7（中台） | 4C8G | 2 | 流程引擎 |
| lowcode 引擎（中台） | 4C8G | 2 | 低代码运行 |
| Nacos 2.3 / Sentinel 1.8 | 4C8G | 各 2 | 注册配置/流控 |
| Prometheus+Grafana+Loki+SkyWalking | 8C16G | 各 2 | 可观测 |

### 1.3 网络与安全要求

- 生产 HTTPS（TLS 1.2+，推荐 1.3），证书由 KMS 签发与自动轮换；
- 数据库/中间件仅应用网段可达，管理端口禁公网；
- K8s NetworkPolicy 限定命名空间互通；`/api/service/v1/internal/**` 仅 mTLS 服务间与执行端可达；
- 密钥/口令由 KMS + K8s Secret 管理，禁止硬编码；
- RPA 执行端独立网段，凭准入凭证接入，目标系统访问受白名单约束。

## 4 部署步骤（容器/脚本）

### 4.1 构建与镜像

```bash
# 1) 构建后端（api + worker 同镜像，按 profile 启动）
mvn -T 4 clean package -DskipTests -P prod

# 2) 构建镜像（多阶段，非 root）
docker build -t registry.fenglincloud.com/service/fenglin-service-service:1.0.0 .

# 3) 前端
pnpm -C fenglin-hub-admin-ui install && pnpm -C fenglin-hub-admin-ui build   # /admin/service
pnpm -C fenglin-hub-portal-ui install && pnpm -C fenglin-hub-portal-ui build # /app/service

# 4) 执行端（客户侧）
docker build -t registry.fenglincloud.com/service/fenglin-service-rpa-agent:1.0.0 ./rpa-agent

# 5) 镜像签名 + 推送
cosign sign --key kms://service-sign registry.fenglincloud.com/service/fenglin-service-service:1.0.0
docker push registry.fenglincloud.com/service/fenglin-service-service:1.0.0
```

### 4.2 数据库迁移（Flyway，强制）

```bash
# 迁移由发布流水线自动执行；禁止手工改库
flyway -url=jdbc:postgresql://pg-primary:5432/fenglin_service \
       -user=svc_migrator -locations=filesystem:./db/migration \
       -baselineOnMigrate=false migrate
# 脚本：V1_0_1__init_service_schema.sql ... V1_0_20__archive_partition_jobs.sql
```

迁移顺序（与 FL-SVC-DB-003 第 8 章一致）：`V1_0_1` 基线建表 → `V1_0_2` 索引 → `V1_0_3` RLS 策略 → `V1_0_4` PII 加密列与 `phone_hash` → … → `V1_0_20` 分区与归档任务。迁移前自动快照，失败自动回滚并阻断发布。

### 4.3 K8s 部署

```bash
# 1) 配置与密钥
kubectl -n fenglin-service create secret generic svc-secret \
  --from-literal=DB_PASSWORD="$SVC_DB_PASSWORD" \
  --from-literal=REDIS_PASSWORD="$SVC_REDIS_PASSWORD" \
  --from-literal=KMS_KEY_ID="$SVC_KMS_KEY_ID" \
  --from-literal=RPA_CRED_KMS_KEY_ID="$SVC_RPA_CRED_KMS_KEY_ID" --dry-run=client -o yaml | kubectl apply -f -

# 2) 应用部署（ArgoCD GitOps 同步）
kubectl -n fenglin-service apply -f k8s/api-deployment.yaml       # api + HPA + PDB
kubectl -n fenglin-service apply -f k8s/worker-deployment.yaml    # worker
kubectl -n fenglin-service apply -f k8s/scheduler-deployment.yaml # job-scheduler（主备）
kubectl -n fenglin-service apply -f k8s/service.yaml
kubectl -n fenglin-service apply -f k8s/networkpolicy.yaml
kubectl -n fenglin-service apply -f k8s/ingress.yaml              # /api/service/v1 路由

# 3) 校验
kubectl -n fenglin-service rollout status deploy/fenglin-service-service
kubectl -n fenglin-service get pods -l app=fenglin-service-service
curl -s https://service.fenglincloud.com/actuator/health | jq .
```

`api-deployment.yaml` 关键片段：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: fenglin-service-service, namespace: fenglin-service }
spec:
  replicas: 8
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 2, maxUnavailable: 0 }
  template:
    spec:
      securityContext: { runAsNonRoot: true, runAsUser: 10001 }
      containers:
        - name: app
          image: registry.fenglincloud.com/service/fenglin-service-service:1.0.0
          args: ["--spring.profiles.active=prod,api"]
          resources:
            requests: { cpu: "2", memory: 4Gi }
            limits:   { cpu: "6", memory: 12Gi }
          readinessProbe: { httpGet: { path: /actuator/health/readiness, port: 8080 }, initialDelaySeconds: 30 }
          livenessProbe:  { httpGet: { path: /actuator/health/liveness,  port: 8080 }, initialDelaySeconds: 60 }
          envFrom: [{ secretRef: { name: svc-secret } }]
```

### 4.4 机器人执行端（客户侧）部署

```bash
# 1) 生成准入凭证（管理端「RPA 治理 → 机器人与配额」下发）
# 2) 执行端配置（独立网段，仅出网至网关 mTLS 端口）
# 3) 启动
docker run -d --name svc-rpa-agent --restart=always \
  -e SVC_GATEWAY_MTLS=https://gateway.fenglincloud.com:8443 \
  -e SVC_ROBOT_TOKEN=<robot-token> \
  -e SVC_AGENT_DATA=/data/rpa \
  -v /data/rpa:/data/rpa \
  registry.fenglincloud.com/service/fenglin-service-rpa-agent:1.0.0
# 4) 校验：管理端机器人列表状态 ONLINE，心跳正常
```

执行端原则：仅主动出网（拉取任务 + 回调）；不开放入站端口；凭据经一次性临时令牌换取；截图本地暂存后上传并按保留策略清理。

### 4.5 发布流水线（GitLab CI + ArgoCD）

```
commit → 单元测试 → SAST/SCA/镜像扫描 → 构建签名 → 推送仓库
      → 部署 staging → 集成/回归（TC 回归组 R1–R8）→ Flyway 迁移（prod 预检）
      → ArgoCD 灰度发布 prod → 观测窗口 → 全量
```

## 6 灰度与回滚

### 6.1 灰度策略（Argo Rollouts）

| 阶段 | 流量比例 | 观测窗口 | 通过条件 |
|---|---|---|---|
| 金丝雀 | 5% | 10min | 错误率 ≤0.1%，P95 ≤300ms，无异常日志 |
| 分批放量 | 30% → 50% | 各 10min | 同上且业务指标正常（提单成功率、任务成功率、发布成功率） |
| 全量 | 100% | 30min 值守 | 同上 |

灰度按租户白名单 + 流量比例双维度；管理端配置类变更同步灰度；数据库迁移采用**向前兼容**策略（先加列后切换，禁止破坏性 DDL）；**执行端版本与后端契约保持兼容**，灰度期间执行端双版本并存。

### 6.2 回滚

```bash
# 应用回滚（Argo Rollouts）
kubectl argo rollouts undo deployment/fenglin-service-service -n fenglin-service

# 或指定版本
kubectl argo rollouts set image deployment/fenglin-service-service \
  app=registry.fenglincloud.com/service/fenglin-service-service:0.9.9 -n fenglin-service

# 执行端回滚（保留正在运行任务完成后切换）
docker rm -f svc-rpa-agent && docker run ... fenglin-service-rpa-agent:0.9.9
```

触发回滚条件：错误率 >0.5% 持续 5min、P95 >500ms 持续 10min、S1 缺陷、数据异常、任务状态错乱。应用回滚 SLA ≤5 分钟；数据库回滚仅允许通过后续 Flyway 补偿脚本（不回退已执行脚本），并保留现场数据；低代码应用发布回滚走能力契约 `SVC-CAP-007`（快照回滚）。

## 7 监控告警

### 7.1 监控指标

| 层面 | 指标 | 阈值/告警 |
|---|---|---|
| 应用 | QPS、P95/P99、错误率、JVM GC、线程池 | P95 >300ms 或错误率 >0.5% 告警 |
| 网关 | 请求量、限流次数、鉴权失败率 | 限流突增、401/403 异常升高告警 |
| 数据库 | CPU、连接数、慢查询、复制延迟 | CPU >75%、复制延迟 >30s 告警 |
| Redis | 命中率、内存、集群健康 | 命中率 <90%、内存 >80% 告警 |
| Kafka | 消费滞后、分区均衡 | 滞后 >10 万条告警 |
| ES | 集群状态、查询延迟 | 状态非 green、P95 >200ms 告警 |
| SLA 任务 | 计时准确性、升级成功率 | 升级失败、计时漂移 >30s 告警 |
| RPA | 心跳在线率、任务成功率、队列深度、重试率、转人工率 | 在线率 <90%、成功率 <95%、队列积压 >500 告警 |
| 挖掘 | 发现任务成功率、耗时 | 失败或超 30min 告警 |
| 执行端 | 主机资源、目标系统可达性、凭据换取失败 | 异常告警（含白名单拦截） |
| 可用性 | `/actuator/health`、合成拨测 | 不可用立即告警（P0） |

### 7.2 告警分级与通知

| 级别 | 场景 | 通知渠道 | 响应 |
|---|---|---|---|
| P0 | 服务不可用、数据异常、安全事件 | 电话 + 企微/飞书 + 邮件 | 5min 内响应 |
| P1 | 核心指标劣化、任务失败、执行端大面积离线 | 企微/飞书 + 邮件 | 15min 内响应 |
| P2 | 非核心告警、容量预警 | 邮件 | 当日处理 |
| P3 | 巡检提示 | 工单 | 计划内处理 |

告警规则由 Prometheus + Alertmanager 定义，纳管于 Git（IaC）；告警须可抑制、可静默、可追溯到值班人。

## 8 备份恢复

### 8.1 备份策略

| 对象 | 策略 | 保留 |
|---|---|---|
| PostgreSQL | 每日全备 + 每 15min WAL 归档（PITR） | 全备 30 天、WAL 7 天 |
| 对象存储（MinIO） | 版本控制 + 每日增量（含截图、导入报告） | 按生命周期 90 天（截图 30 天） |
| ES 索引 | 每日快照到对象存储 | 30 天 |
| Redis | AOF + 每日 RDB | 7 天 |
| 配置（Nacos） | 每日导出 + Git 版本 | 永久 |
| K8s 资源 | GitOps 仓库版本化 | 永久 |
| 执行端配置 | 版本化 + 凭证可重新下发 | 永久 |

异地容灾：WAL 与全备异地异步复制；同城双活 + 异地备份，RPO ≤5min、RTO ≤30min（演练实测 RPO 2.4min / RTO 18min）。

### 8.2 恢复流程

```bash
# 1) 数据库 PITR 恢复
pg_basebackup -D /var/lib/pgsql/restore -h pg-backup
# 配置 recovery_target_time 后启动，按时间点恢复至故障前

# 2) 校验
psql -c "SELECT count(*) FROM svc_ticket;"       # 关键表行数校验
psql -c "SELECT count(*) FROM svc_robot_task;"    # 任务表校验
# 3) 应用指向新实例并回归核心链路（TC 回归组 R1、R4、R7）
```

恢复演练：每季度一次，覆盖误删数据、库故障、可用区故障、执行端凭证失效四类场景；演练报告归档。

## 9 巡检与应急预案

### 9.1 巡检清单

| 频率 | 项目 |
|---|---|
| 每日 | 服务健康、告警清零、SLA 任务与 RPA 调度成功、备份完成、磁盘/容量水位、执行端在线率 |
| 每周 | 慢查询 TOP、限流统计、SLA 计时准确性抽检、任务失败 TOP、审计异常、安全告警（白名单拦截） |
| 每月 | 容量趋势、依赖版本漏洞、KMS 密钥轮换状态（含 RPA 凭据）、权限复核 |
| 每季度 | 容灾演练、恢复演练、压测基准回归、安全复评、沙箱与白名单策略复核 |

巡检结果记录于运维台账；异常转工单并闭环。

### 9.2 应急预案

| 场景 | 现象 | 处置步骤 |
|---|---|---|
| 服务不可用 | health 失败、5xx 上升 | 1) 确认范围 2) 检查网关/依赖 3) 扩容或回滚 4) 恢复后回归 |
| 数据库故障 | 连接失败、复制中断 | 1) 主从切换 2) 校验一致性 3) 修复原主并重建复制 |
| 中间件异常 | Kafka 积压/Redis 抖动/ES 红 | 1) 降级（缓存击穿保护/检索降级）2) 扩容或重启 3) 补数据 |
| SLA 计时异常 | 计时漂移、升级未触发 | 1) 暂停 tick 任务 2) 校验日历与策略 3) 重算（幂等）4) 恢复 |
| 机器人执行端大面积离线 | 在线率骤降 | 1) 检查执行端网络与凭证 2) 重新下发准入凭证 3) 任务按幂等延迟重投 4) 转人工兜底 |
| RPA 任务积压 | 队列深度上升 | 1) 扩容执行端/并发 2) 检查目标系统可达性 3) 暂停非核心调度 |
| 凭据换取失败 | `6007004` 频发 | 1) 检查 KMS 与凭据状态 2) 轮换凭据 3) 失败任务转人工 |
| 挖掘任务失败 | 发现任务失败/超时 | 1) 分片重试（幂等）2) 保留上次结果 3) 定位慢数据源 |
| 工作流任务堆积 | 流程超时升级增多 | 1) 扩容工作流实例 2) 检查节点路由 3) 人工兜底推进 |
| 安全事件 | 越权/白名单拦截异常/凭据异常 | 1) 隔离账号与执行端 2) 审计溯源 3) 加固 4) 按安全事件流程上报 |
| 误删数据 | 数据缺失 | 1) PITR 恢复至故障前 2) 校验 3) 回归核心链路 |

值班与升级：一线运维（7×24）→ 二线研发值班 → 三线架构/安全；P0 事件 15 分钟内成立应急小组，30 分钟内对外通报进展，事后 3 个工作日内提交复盘报告。
