**关键配置**：
- 每个 Deployment 配置 `readinessProbe`/`livenessProbe`/`startupProbe` + `preStop` 优雅停机（sleep 15s）+ `PodDisruptionBudget`（minAvailable 50%）；

- 拓扑分布约束 `topologySpreadConstraints` 跨可用区均衡；
- 配置与密钥经 Nacos / K8s Secret / KMS，禁止硬编码。

### 3.4 共享模块打包与依赖有效性校验

**背景（真实反例）**：2026-11-14 19:26 重建 IAM 时 Maven 返回 `BUILD SUCCESS`，fat jar 时间戳也是新的，但 jar 内 `BOOT-INF/lib/fenglin-common-web` 仍是 11-10 的 8450 字节旧包，缺少 `handleNotFound`。结果未匹配路由的 `NoResourceFoundException` 落入通用异常处理，返回 `500 FL-COMMON-0500` 而不是 `404 FL-COMMON-0404`。19:47 先 `install` 共享模块、再重建后恢复正常。**构建成功和时间戳都不能证明依赖是新的。**

**强制规则**：

1. 批量打包或离线打包前，先安装共享模块，确保 `~/.m2` 与源码一致：

   ```bash
   mvn -pl fenglin-common/fenglin-common-web -am install -DskipTests
   ```

   多模块统一发布时，应在同一 reactor 内先 `install` 再 `package`，不要跳过共享模块。

2. **硬判据（决定退出码）**：解出 fat jar 内 `BOOT-INF/lib/fenglin-common-web-*.jar`，用 `javap` 检查 `com.fenglin.common.web.ApiExceptionHandler` 必须同时存在 `handleBizException`、`handleValidation`、`handleMissingParameter`、`handleTypeMismatch`、`handleNotFound`、`handleUnexpected` 六个方法；缺任一即 `FAIL`。fat jar 内缺少该 artifact 也判 `FAIL`（网关除外）。

3. **软判据（只告警）**：内嵌 artifact 的 SHA256 与 `~/.m2` 当前版本不一致仅记 `WARN`，不影响退出码。**字节相等不是正确性的必要条件**：本次 13 个 `AF854C84…` 服务即为反例——它们是同一份源码的另一次构建，方法集完整、直连未知路径返回 `404 FL-COMMON-0404`，仅字节不同。

4. **辅证**：发布前可直连各服务端口打未知路径，应返回 `404 FL-COMMON-0404`。经网关的探针不能作为下游证据：网关对未匹配路径会返回自己的 404（无 `code`）。

5. 发布前必须执行仓库脚本，硬判据失败（非 0）即阻断发布：

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify-common-web.ps1 -Root .
   ```

   输出逐服务一行：服务、大小、SHA256、方法集是否完整、字节判定（`CURRENT/STALE/NO_BASELINE`）、最终结论（`PASS/WARN/FAIL`）。`gateway` 标记 `NO_DEP`，判 `PASS`。脚本可重复执行，退出码只由硬判据决定。

**CI 接入位置**：仓库已有 `.github/workflows/ci.yml`。构建步骤由 `mvn ... clean verify` 调整为 `mvn ... clean install`（生成 `~/.m2` 基线），其后新增 `Verify common-web handler set` 步骤：

```yaml
      - name: Verify common-web handler set
        shell: pwsh
        run: ./scripts/verify-common-web.ps1 -Root .
```

**判定口径说明**：

- `PASS`：六个方法齐全；字节与 `~/.m2` 一致，或为网关 `NO_DEP`。
- `WARN`：六个方法齐全，但 SHA256 与 `~/.m2` 不一致（或 CI 无基线）；可发布，仅提示构建批次不同。
- `FAIL`：缺 artifact、缺任一方法、`javap` 执行失败或 fat jar 缺失；阻断发布。
- `CURRENT/STALE` 只是字节信号，不再单独决定成败。

**2026-11-14 审计结论**：21 个服务中 6 个曾内嵌 8450 字节旧包（`collab/crm/rnd/search/service/talent`），已全部重建；IAM 于 19:48 重建。新门禁实测 `PASS=8 / WARN=13 / FAIL=0`，退出码 0；13 个 `WARN` 即上述同源码另一次构建。详细清单见 `2026-11-14/plat24-data-scope/outputs/common-web-audit.md`。

### 3.5 CI 测试 job 分工

`.github/workflows/ci.yml` 按“是否依赖外部服务”拆为三个 job，push 与 PR 并行触发；三者都是必需检查。

| job | 范围 | 外部依赖 | 实现方式 |
|---|---|---|---|
| `backend` | 单元、迁移、bootstrap、各服务集成测试 | 无（不要求 MinIO/Redis/ES） | surefire 负向过滤：`-Dtest='!FileFlowIntegrationTest,!SearchIntegrationTest,!OpenApiIntegrationTest' -Dsurefire.failIfNoSpecifiedTests=false`，命令仍为 `clean install` |
| `external-integration` | 文件、搜索、开放平台三条真实链路 | MinIO `9000`、Elasticsearch `9200`、Redis `6379`（service 容器） | `-Dtest='FileFlowIntegrationTest,SearchIntegrationTest,OpenApiIntegrationTest'`，容器健康检查通过后执行 |
| `common-web-gate` | 共享模块依赖有效性 | 无 | 3.4 节脚本，未调整 |

**测试自持约束**：`backend` 内的集成测试不得隐式依赖本机中间件。租户开通的财务域调用、审计服务健康检查分别用测试替身与 Zonky 内嵌 PostgreSQL 隔离；新增用例时必须沿用该口径，避免“本机有服务所以绿、CI 红”。

**实测（2026-11-14，run `43604245963`）**：`backend` success（`TalentIntegrationTest` 19/19，finance/rnd/service/legal/intelligence 均实际执行）；`external-integration` success（File 6、Search 4、OpenApi 8）；`common-web-gate` success。

## 4 中间件部署

### 4.1 Nacos 2.3.x

- 3 节点集群，MySQL（或内嵌 Derby 仅测试）持久化；命名空间 `fenglin-hub-{env}`；
- 服务注册发现 + 配置中心；开启鉴权，账号最小权限。

### 4.2 PostgreSQL 15

- Patroni 主备 + etcd 仲裁；同步复制（`synchronous_commit=remote_apply`）；
- 只读副本分流查询；PgBouncer 连接池；
- 关键参数：`shared_buffers=16GB`、`work_mem=64MB`、`max_connections=500`（配合 PgBouncer）、`archive_mode=on`（WAL 归档）；
- Flyway 迁移由专用 Job 执行，账号仅 DDL 权限，应用账号仅 DML。
- 分区表 DDL 身份（PLAT-20，已完成收口）：
  - DDL 使用独立登录角色 `fl_login_ddl` + `SET ROLE fl_ddl_owner`，与业务连接池的 `fl_app` 完全分离；
  - `fl_ddl_owner` 是五张分区表（`hub_audit_log`、`hub_message`、`hub_api_call_log`、`hub_ai_metering`、`hub_metering`）及其全部子分区（含 `_default`）的属主，角色属性为 `NOLOGIN NOSUPERUSER NOBYPASSRLS`；
  - **`fl_ddl_owner` 对 RLS 免疫**（表 `relforcerowsecurity = f`，属主默认绕过 RLS），**只用于分区维护 DDL，禁止用于任何业务查询**；
  - 口令只通过用户级环境变量 `FL_LOGIN_DDL_PASSWORD` 注入（生产用 K8s Secret），不写入仓库；
  - 配置前缀 `fenglin.db.ddl.*`（`url` / `username` / `password` / `role`，默认角色 `fl_ddl_owner`），单连接用后即关，连接建立后强制 `SET ROLE`；
  - 启动自检（fail-fast）：`session_user = fl_login_ddl`、`current_user = fl_ddl_owner`、`has_schema_privilege('fenglin_hub','CREATE') = true`、`rolsuper = false`、`rolbypassrls = false`；任一不满足记录 ERROR 并以非 0 退出，不允许降级运行。

### 4.3 Redis 7

- 主从 + 哨兵（3 哨兵）；开启 ACL 与 `requirepass`；持久化 AOF（everysec）+ RDB；
- 用途：会话、令牌黑名单、限流、幂等键、缓存。

### 4.4 Kafka 3.6

- 3 Broker；`default.replication.factor=3`、`min.insync.replicas=2`；
- Topic 规划：`hub.tenant.*`、`hub.user.*`、`hub.workflow.*`、`hub.message.*`、`hub.audit.*`、`hub.metering.*`、`hub.ai.*`；分区 ≥ 6。

### 4.5 Elasticsearch 8

- 3 节点，分片副本 ≥ 1；开启安全认证（内网亦启用）；
- 平台索引 `hub_*` + 8 域索引；IK 分词插件；生命周期 ILM 冷热分层。

### 4.6 MinIO

- 4 节点纠删码；桶：`hub-files`、`hub-reports`、`hub-archive`、`hub-backup`；
- 禁用公开桶，访问走签名 URL；开启版本控制与服务端加密。

### 4.7 其他

- **XXL-Job**：2 执行器，承载计量归集、审计归档、索引重建、超时催办、分区预建；
- **SkyWalking OAP**：2 节点，接收链路追踪；
- **Prometheus/Grafana/Loki**：指标/可视化/日志。

## 5 灰度发布与回滚

### 5.1 发布策略

| 策略 | 适用 | 说明 |
|---|---|---|
| 滚动发布 | 常规变更 | 分批替换，`maxUnavailable=25%` |
| 蓝绿发布 | 网关/核心中台 | 双环境，流量切换 |
| 灰度发布 | 高风险变更 | 按租户/用户/比例路由 |

### 5.2 灰度发布流程

```
① 部署新版本（不导流量，Standby）
② 配置灰度规则（租户白名单 → 用户白名单 → 百分比）
③ 观察期（≥30min）：错误率、P95、告警
④ 全量发布（逐步放量 5%→20%→50%→100%）
⑤ 观察稳定后收敛
```

- 灰度规则由网关承载（`platform:gw:gray:manage`），支持粘滞（同一用户稳定命中）；
- 前端发布：静态资源 CDN 版本化 + 特性开关（Feature Flag）。

### 5.3 回滚

| 场景 | 动作 | 目标时限 |
|---|---|---|
| 应用异常 | 回滚镜像版本（ArgoCD `rollback`） | ≤ 5min |
| 数据库迁移 | 前向兼容脚本（避免破坏性 DDL）；必要时反向脚本 | ≤ 30min |
| 网关路由 | 切回旧版本路由 | ≤ 1min |
| 配置错误 | Nacos 配置回滚 + 推送 | ≤ 1min |

**原则**：数据库变更必须向前兼容（新增列可空/默认值），禁止在发布中执行破坏性 DDL；灰度回滚演练目标 ≤ 5min（实测 128s）。

### 5.4 令牌与签名密钥（PLAT-10）

| 项 | 当前行为 | 重启/发布影响 | 生产要求 |
|---|---|---|---|
| RSA 签名密钥 | auth 启动时在内存生成（dev） | 换钥后全部已签发 access token 验签失败（401）；实现 401→refresh 的端可用 refresh token 无感恢复，脚本、第三方直连、导出链路会中断 | 必须改为 KMS 或固定密钥文件（K8s Secret 挂载），**多副本共享同一密钥**，否则副本间验签随机失败 |
| access token | 864B，TTL 2h，claims 只含 `roles`+`pv` | 无影响 | 兼容期旧令牌（含 `permissions` claim）继续可用，自然过期后收敛 |
| 权限解析缓存 | 网关 L1 60s + Redis L2 10min，键 `tenant:user:pv` | 网关重启 L1 清空、L2 命中，无感 | 权限变更 ≤60s 生效；Redis 故障降级 L1 10s；auth 故障 fail-close 503 `FL-COMMON-0503` |
| 发布顺序 | — | 先滚动 auth（保持同一密钥）再滚动网关 | 禁止多副本 auth 各自生成密钥；未完成密钥持久化前，重启 auth 视为"全员重登"事件，需避开业务高峰 |

> 结论：**未落地密钥持久化之前，不允许把 auth 重启当作普通滚动发布**。对应缺口见总账 PLAT-15（阻塞）。

## 6 监控告警

### 6.1 监控体系

| 维度 | 工具 | 内容 |
|---|---|---|
| 指标 | Prometheus + Grafana | JVM、QPS、RT、错误率、连接池、中间件指标 |
| 日志 | Loki（采集）+ 结构化 JSON | 全服务日志，`X-Request-Id` 检索 |
| 链路 | SkyWalking | 全链路追踪（`X-Trace-Id`） |
| 业务 | 自研业务看板 | 租户用量、配额、SLA、待办积压、审计告警 |

### 6.2 核心指标与阈值

| 指标 | 阈值 | 告警级别 |
|---|---|---|
| 网关 P95 响应 | > 300ms 持续 5min | P2 |
| 接口错误率 | > 1% 持续 5min | P1 |
| JVM GC 停顿 | P99 > 300ms | P2 |
| CPU 使用率 | > 80% 持续 10min | P2 |
| DB 连接池使用率 | > 85% | P2 |
| 磁盘使用率 | > 80% | P2 |
| 可用性（黑盒探测） | < 99.99%（滚动） | P1 |
| 审计链校验失败 | 任意一次 | P0 |
| 跨租户访问尝试 | 任意一次 | P0 |
| 配额使用率 | ≥ 80% / 100% | P3 / P2 |
| 工作流超时任务 | > 阈值 | P3 |

### 6.3 告警通道

- P0/P1：电话 + 短信 + 企微/飞书群；
- P2：企微/飞书群 + 邮件；
- P3：站内信/邮件；
- 告警收敛（同源聚合）、抑制（维护窗口）、升级（15min 未响应升级）。

## 7 备份与恢复

### 7.1 备份策略

| 对象 | 方式 | 频率 | 保留 |
|---|---|---|---|
| PostgreSQL | pg_basebackup 全备 + WAL 归档 | 每日全备 + 持续增量 | 30 天（异地 90 天） |
| Redis | RDB + AOF | 每小时 RDB | 7 天 |
| Elasticsearch | 快照（snapshot） | 每日 | 14 天 |
| MinIO | 跨集群复制 | 实时/每小时 | 30 天 |
| Kafka | 副本（非备份） | — | Topic 保留策略 |
| 配置 | Nacos 配置导出 + Git | 每次变更 | 永久（Git） |

### 7.2 恢复演练

| 场景 | RTO 目标 | 实测 |
|---|---|---|
| 单 Pod 故障 | 自动重调度 ≤ 1min | 35s |
| 数据库主备切换 | ≤ 30min | 42s |
| 整机房故障（双活切换） | ≤ 30min | 8min |
| 数据误删恢复（PITR） | ≤ 30min | 18min |

**备份校验**：每月抽样恢复验证；季度完整演练并记录；备份加密（AES-256）。

## 8 巡检与应急预案

### 8.1 日常巡检清单

| 频率 | 项目 |
|---|---|
| 每日 | 服务健康、SLA、错误率、告警、慢查询、磁盘/连接池、备份成功 |
| 每周 | 证书有效期、配额使用、日志异常、安全告警复核 |
| 每月 | 依赖漏洞扫描、备份恢复抽样、容量趋势分析、索引健康 |
| 每季度 | 容灾演练、账号复核、权限审计、密钥轮换核查 |

### 8.2 应急预案

| 场景 | 应急措施 |
|---|---|
| 网关不可用 | 摘除故障 Pod + 扩容 + 切换备用入口；必要时降级非核心路由 |
| 认证服务异常 | JWKS 本地缓存兜底；缩短令牌有效期；修复后恢复 |
| 数据库故障 | Patroni 自动切换；只读副本提升；应用重连重试 |
| Redis 故障 | 降级本地缓存；限流放宽（风险窗口）；修复后恢复 |
| Kafka 积压 | 扩容消费者 + 增加分区；必要时降级非关键事件 |
| ES 故障 | 搜索降级数据库检索；重建索引 |
| AI 模型不可用 | 多模型路由 → 降级检索 → 提示用户 |
| 突发大流量 | 限流 + HPA 扩容 + CDN 缓存；必要时临时封禁异常来源 |
| 数据安全事件 | 立即隔离 + 冻结账号会话 + 取证（审计）+ 上报 |

**应急流程**：发现 → 定级 → 通知（值班/升级）→ 处置 → 恢复验证 → 复盘（RCA）→ 改进。

## 9 SaaS 与私有化部署方案

### 9.1 SaaS 多租户方案

| 项 | 方案 |
|---|---|
| 隔离 | 共享库 + `tenant_id` + RLS |
| 部署 | 多云/多可用区 K8s，共享中间件（逻辑隔离+配额） |
| 网络 | 公网 HTTPS（WAF），多租户共享入口 |
| 升级 | 平台统一灰度升级 |
| 计量 | 多租户计量归集与出账 |
| 适用 | 中小客户、快速开通 |

### 9.2 私有化单租户方案

| 项 | 方案 |
|---|---|
| 隔离 | 独立库（database per tenant），物理隔离 |
| 部署 | 客户内网/专有云 K8s，独立中间件 |
| 网络 | 内网部署，可选 VPN/专线回连 SaaS 智能中台 |
| 许可 | License 文件（含产品/席位/有效期） |
| 升级 | 版本包 + 升级脚本 + 回滚预案；支持离线镜像 |
| 适用 | 大型客户、强合规要求 |

### 9.3 混合方案

- 核心业务数据私有化部署（独立库），智能中台（search/ai/report）SaaS 化；
- 经 `/internal/**` mTLS 打通，数据脱敏后出域；
- 计量与计费统一归集至平台。

### 9.4 私有化部署检查清单

1. 环境预检（K8s 版本、节点资源、网络策略、存储类）；
2. 中间件部署与连通性验证；
3. 平台镜像加载与签名校验；
4. 数据库迁移与内置数据初始化；
5. License 导入与校验；
6. SSO 对接（客户 IdP）验证；
7. 冒烟测试 + 性能抽测；
8. 监控接入与告警配置；
9. 备份策略配置与首次备份；
10. 交付文档与运维交接。
