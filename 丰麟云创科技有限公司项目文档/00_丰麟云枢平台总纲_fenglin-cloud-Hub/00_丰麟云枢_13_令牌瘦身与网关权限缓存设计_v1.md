# 丰麟云枢 · 令牌瘦身与网关权限缓存设计方案（PLAT-10）

> 版本：v1（2026-11-10）
> 状态：**仅设计，不改代码**。落地需另行评审与排期。
> 关联：`99_跨产品缺口总账_v1.md` 中 PLAT-10（JWT 过大阻塞）、PLAT-11（生产网关大 header 部署项）。

---

## 1. 问题与实测数据

### 1.1 现场实测（2026-11-10，平台管理员 admin @ fenglin 租户）

| 指标 | 实测值 | 说明 |
|---|---|---|
| access_token 总长度 | **16 970 字符**（约 16.6 KB） | `Authorization: Bearer ...` 单头即 17 KB |
| `permissions` 声明条目数 | **456 个** | 平台管理员拥有全量权限点 |
| `permissions` 序列化长度 | **11 182 字符** | 占令牌 66% |
| `roles` 声明 | **缺失（空）** | 网关 `GatewayPrincipal.roles` 解析了但签发侧从未写入 |
| access token TTL | 2 小时（`AuthProperties.accessTokenTtl`） | 权限变更最长滞后 2h |
| refresh token TTL | 7 天 | refresh 时重新查权限 |
| 网关注入头 | `X-Permissions`（逗号分隔全部权限点） | 约 11 KB |
| 单请求头合计（Authorization + X-Permissions） | **约 28 KB** | 已超过 Tomcat 默认 8 KB、Nginx 默认 8 KB |

### 1.2 造成的影响

1. **Tomcat 默认 8KB 头上限直接拒绝**：管理员带完整权限访问部分服务返回 400 `Request header is too large`，业务不可用。已用 21 个服务统一 `max-http-request-header-size: 64KB` 止血（PLAT-10 保持开启，属临时措施）。
2. **生产链路仍是隐患**（PLAT-11）：Nginx `large_client_header_buffers` 默认 4×8KB，K8s ingress-nginx 默认 `large-client-header-buffers: 4 8k`；64KB 头会在入口层被 400/431 掉，且部分 CDN/WAF 只允许 16KB。
3. **权限规模线性膨胀**：单个权限点平均 24 字符，权限点随产品线增长；未来 800~1000 个权限点时单请求头将逼近 60 KB，64KB 止血也会失效。
4. **每次请求都要携带并解析全量权限**：网关每请求 `String.join` 一次 11 KB 字符串，下游 `PermissionGuard` 每处调用重复 `split` 建 `Set`（全仓 89 个文件、827 处调用）。
5. **权限变更生效慢**：只能靠 refresh（最长 2h）或重新登录，管理端改角色权限后用户端"看起来没生效"。

### 1.3 现状链路（代码位置）

```
登录  AuthService.login                                        // AuthService:87
      ├─ permissionQueryMapper.findPermissionCodes(userId)     // AuthService:141  → 456 条
      ├─ JwtTokenService.accessToken(... permissions ...)      // AuthService:142  写进 permissions claim
      └─ 返回 access + refresh + id_token

刷新  AuthService.refresh                                      // AuthService:154
      └─ 重新查权限并重新签发 access token                      // AuthService:202-203

网关  AuthGlobalFilter.filter                                  // AuthGlobalFilter:51
      ├─ JwtVerifier.verify（本地 RSA 验签，无状态）
      ├─ 校验 token_use=access / tenant_id / user_id / client_type
      ├─ RevocationChecker.isRevoked(jti)（Caffeine 30s，fail-open）// RevocationChecker:34-56
      └─ 注入 X-Tenant-Id / X-User-Id / X-Client-Type / X-Permissions  // AuthGlobalFilter:32

下游  PermissionGuard.require(header, "xxx")                   // PermissionGuard:22/32/52
      └─ 逗号切分 + Set.contains（827 处调用）                   // PermissionGuard:56-62
```

关键约束：**下游 18 个业务服务只认 `X-Permissions` 请求头，接口签名不感知令牌内容**。因此任何方案都必须保留"网关注入 `X-Permissions`"这一层，否则要改 827 处调用与全部集成测试。

## 2. 目标与非目标

### 2.1 目标

| 编号 | 目标 | 量化 |
|---|---|---|
| G1 | access token 体积与权限点数量解耦 | 任意用户 token ≤ 1.5 KB |
| G2 | 单请求头总量回到安全区 | Authorization + X-Permissions ≤ 8 KB（默认值内，无需改 Nginx） |
| G3 | 权限变更生效时效可接受 | 目标 ≤ 60s（当前 ≤ 2h） |
| G4 | 下游零改动 | `PermissionGuard` 与 827 处调用不变 |
| G5 | 撤销语义不退化 | 登出/踢下线仍按现有 jti 撤销即时生效 |
| G6 | 可灰度、可回滚 | 单开关切回旧签发/旧解析 |

### 2.2 非目标

- 不引入 OPA/Casbin 等外部策略引擎（超出当前交付范围）。
- 不改造 id_token / refresh_token 的既有语义。
- 不在本轮改动服务端鉴权模型（仍为"网关集中 + 下游二次校验"）。
- 不做权限点本身的收敛/合并（属 IAM 产品侧优化，另行立项）。

## 3. 方案对比

### 方案 A：JWT 只留角色 + 权限版本号，网关每次回源 auth

- JWT claims：`sub / tenant_id / tenant_code / client_type / sid / roles[] / pv / jti / token_use / scope`
- 网关去掉 `permissions`，改为用 `(tenantId, userId, pv)` 调 auth 内部接口取权限，不做本地缓存。
- 优点：实现最简单，权限一致性最强（最坏滞后 = 一次请求）。
- 缺点：每请求一次内部 HTTP（读路径 QPS × 1，网关到 auth 的放大 1:1）；auth 成为新单点，P99 直接叠加 1 次 RPC；不具备生产可行性，仅作对照基线。
- 结论：**不采用**。

### 方案 B：JWT 瘦身 + 网关两级缓存（Caffeine L1 + Redis L2）+ 版本号主动失效

- JWT 与方案 A 相同（无 `permissions`）。
- 网关按 `(tenantId, userId, pv)` 取权限：L1 Caffeine（60s，单机）→ L2 Redis（10min，跨实例共享）→ 回源 auth 内部接口。
- 权限变更时 auth 递增 `pv` 并删除 Redis key；网关 L1 因 key 含 `pv` 自然失效（老 pv 条目 TTL 到期淘汰）。
- 撤销检查（jti）保持现状，与权限缓存互不影响；顺序上先鉴权/撤销、后取权限。
- 优点：token 1KB 级、下游零改动、权限时效 60s、auth 只在缓存 miss 时被调用（预计 < 5% 请求）；O(1) 内存放大可控。
- 缺点：引入 Redis 依赖（网关 + auth 需加 `spring-boot-starter-data-redis`，目前仅 openapi-service 使用）；需新增内部接口与 `pv` 维护点；Redis 故障需定义降级策略。
- 结论：**推荐**。

### 方案 C：保留 permissions，仅做编码压缩（短码字典 / 位图 / 多值头拆分）

- 权限点用字典短码（如 `a1,a2,...`）或位图（456 bit ≈ 57 字节 base64）压进 JWT，仍由网关注入。
- 优点：无新增依赖，网关仍无状态；头体积可降到 1~2 KB。
- 缺点：权限字典本身需要版本化（新增权限点要重发字典）；位图顺序依赖权限表排序，跨租户/跨环境易错；令牌可读性差、排障困难；权限变更时效仍是 2h；不解决"权限规模膨胀"的根因，只是把问题推到字典/位图上。
- 结论：**不采用**（可作为极端情况下的兜底预案）。

### 对比表

| 维度 | A 每次回源 | **B 两级缓存（推荐）** | C 压缩编码 |
|---|---|---|---|
| token 体积 | ≤1.5 KB | **≤1.5 KB** | ~1–2 KB |
| 单请求头总量 | ≤4 KB | **≤4 KB** | ~5 KB |
| 权限生效时效 | 实时 | **≤60s** | 2h（不变） |
| 网关新增依赖 | 无（已有 WebClient） | **Redis** | 无 |
| auth 读放大 | 1:1（每请求） | **<5%（缓存命中）** | 0 |
| 下游改动 | 无 | **无** | 无 |
| 权限规模增长适应性 | 好 | **好** | 差（字典膨胀） |
| 新增故障面 | auth 变单点 | **Redis 故障** | 字典版本错配 |
| 改造量 | 小 | **中** | 中 |
| 结论 | 基线对照 | **采用** | 兜底预案 |

## 4. 推荐方案（B）详细设计

### 4.1 令牌声明变更

| 声明 | 现状 | 目标 | 说明 |
|---|---|---|---|
| `sub` / `tenant_id` / `tenant_code` / `client_type` / `sid` | 有 | 保留 | 不变 |
| `token_use` / `scope` / `iss` / `aud` / `iat` / `exp` / `jti` | 有 | 保留 | 撤销仍依赖 `jti` |
| `permissions` | 456 条 | **删除** | 体积主因 |
| `roles` | 缺失 | **新增**（角色 code 数组，通常 1–5 个） | 便于网关/审计快速判定，也是灰度期兼容锚点 |
| `pv` | 无 | **新增**（`long`，权限版本号） | 缓存键与失效依据 |

预期体积：管理员 token ≈ **0.9–1.1 KB**（RSA256 签名固定 342 字符），降幅 ~94%。

`JwtTokenService` 改动点：`accessToken(...)` 入参由 `List<String> permissions` 改为 `List<String> roles, long permissionVersion`；`refreshToken` / `idToken` 不变（本来就不带权限）。

### 4.2 权限版本号（pv）

**存储**：在 `hub_user` 增加 `permission_version bigint not null default 0`（与 IAM 同库 `fenglin_hub`，auth 只读）。

**递增时机**（均在 IAM 写事务内，与业务变更同事务，保证不漂移）：

| 触发动作 | 涉及接口 | 递增范围 |
|---|---|---|
| 用户角色授予/回收/过期 | IAM `assignRoles` / `revokeRole` | 目标用户 |
| 角色权限点增删 | IAM 角色权限编辑 | 该角色下全部用户（`UPDATE hub_user SET permission_version = permission_version + 1 WHERE id IN (...)`） |
| 角色启用/禁用 | IAM 角色状态变更 | 同上 |
| 权限点禁用/删除 | IAM 权限点管理 | 全租户用户 |
| 租户初始化/自助角色播种 | tenant bootstrap | 该租户管理员 |

> 说明：批量递增在租户内用户量级（万级）内是一条 `UPDATE`，可接受；若后续租户规模上万，可退化为"按角色聚合的版本表 + 用户级覆盖位"（见 §9 风险 R4）。

**为什么不用"角色 code 拼串当缓存键"**：角色权限点变更时角色 code 不变，键不会失效，会出现"改了角色权限但缓存还在"的问题；版本号能覆盖这种变更。

### 4.3 auth 内部接口（新增契约，需补《接口文档》）

```
GET /internal/v1/auth/principals/{userId}/permissions
Header: X-Tenant-Id: <tenantId>
Query : pv=<long>            # 网关希望校验的版本号

200 {
  "code": "0",
  "data": {
    "user_id": "9101",
    "permission_version": 12,
    "roles": ["PLATFORM_ADMIN"],
    "permissions": ["hub:tenant:create", "..."]   # 与现状同一套 code
  }
}
```

- 返回 `permission_version`，网关据此判断是否需要刷新 L1/L2（pv 不匹配则以响应为准，避免令牌 pv 过期导致长期读到旧权限）。
- 该接口复用 `PermissionQueryMapper.findPermissionCodes/findRoleCodes`，不新增 SQL 逻辑。
- 在 `InternalAuthController` 增加方法即可（现有 `revocations`、`sessions/status` 同处）。

### 4.4 网关权限解析器

新增 `PermissionResolver`（`fenglin-gateway/security`），在 `AuthGlobalFilter` 中替换掉"直接读 claim"的两行：

```
顺序：
1) 验签 + token_use + 租户/用户校验（现状不变）
2) RevocationChecker.isRevoked(jti)（现状不变，30s 缓存，fail-open）
3) PermissionResolver.resolve(tenantId, userId, pvFromToken)
   L1: Caffeine key = tenantId:userId:pv, TTL 60s, max 50_000
   L2: Redis  key = fenglin:perm:{tenantId}:{userId}:{pv}
             value = {"roles":[...],"permissions":[...]}, TTL 10min
   回源: auth /internal/v1/auth/principals/{userId}/permissions?pv=
4) headers.set("X-Permissions", String.join(",", resolved.permissions))
```

- **缓存键含 `pv`**：pv 变更后新键必然 miss，老键自然过期，无需全网广播失效（L1 60s 内的旧数据由 pv 隔离，不会与新 token 混用）。
- **L2 TTL 10min > L1 60s**：跨实例复用，冷启动不打穿 auth。
- **fail 策略（与撤销检查不同）**：
  - 撤销检查失败 → fail-open（避免 auth 抖动导致全站不可用，现状如此）。
  - 权限解析失败 → **fail-close 返回 503 `FL-COMMON-0503`**，并带 `Retry-After`。理由：权限缺失时放行等于越权或全站 403；返回 503 是唯一"既不误放行、又不误判越权"的选择。
  - 例外：`permissions` 全集为空且 `roles` 为空时视为"无权限用户"，正常放行注入空头，由下游产生 403（不当作故障）。
- **灰度开关**：`fenglin.gateway.permission-source=jwt|resolver`（默认 `jwt` 兼容旧令牌），`fenglin.gateway.permission-cache.l1-ttl/l2-ttl`、`auth-internal-uri`、`timeout` 沿用 `Revocation` 同款配置风格。

### 4.5 下游零改动

`X-Permissions` 仍是逗号分隔的权限点全量串，`PermissionGuard` 的三处入口（`require` / `requireAny` / `has`）与 827 处调用全部不变。唯一的量变是：请求头从 28 KB 降到 4 KB 以内。

> 可选优化（非本方案必做）：`PermissionGuard` 内部对同一请求的 `X-Permissions` 做一次解析缓存（ThreadLocal），可减少 827 处重复 split；与本次瘦身解耦，建议单独立项。

### 4.6 与撤销检查的联动

| 场景 | 现状 | 方案 B 后 |
|---|---|---|
| 登出 / 踢下线 | 写 `hub_auth_revocation(jti)`，网关照 jti 查（30s 缓存） | **不变** |
| 改密码 / 强制下线 | 同上 | 不变 |
| 角色权限调整 | 等 refresh（≤2h） | 递增 `pv` + 删 Redis key，**≤60s** 生效 |
| 删除用户 | 用户状态校验在 auth `refresh`/`userinfo`，网关只看 token | 不变（token 到期前仍可访问，属既有语义，不在本方案扩大范围） |
| auth 故障 | 撤销 fail-open，放行 | 权限解析 fail-close（503）；建议同时对 `jwt` 模式保留开关以便应急回切 |

要点：**权限缓存不清理撤销缓存**，两者键空间正交（`jti` vs `tenantId:userId:pv`）；撤销令牌后即便权限缓存命中，也会被第 2 步拦下。

## 5. 对登录 / 刷新 / 撤销链路的影响

| 链路 | 影响 | 兼容性 |
|---|---|---|
| 登录 `POST /sso/login` | 少签发 11 KB 权限串；多查一次 `roles`（本来 `userinfo` 也查）；建议**同步预热** L2 缓存（登录后 1 次 SET），把首个请求的 miss 消化在登录路径 | 响应体 `TokenPayload` 不变 |
| 刷新 `POST /sso/token:refresh` | 不再查询 456 条权限（只需 `roles` + `pv`），刷新 RT 下降；仍沿用会话/refresh token 轮换与宽限期逻辑 | 不变 |
| 撤销 `POST /sso/token:revoke` / 登出 | 不变（jti 维度） | 不变 |
| `GET /sso/userinfo` | 仍可返回完整 `permissions`（前端菜单/按钮权限依赖它） | 不变 |
| 网关鉴权 | 每请求多 1 次缓存读（L1 命中为纯内存）；miss 时多 1 次内部 RPC | 灰度期双读 |
| 前端 | access token 变小后，`localStorage`/Header 组装、SSE/WebSocket 首帧都更安全 | 无感 |

**灰度期双读**：网关同时支持
- 令牌含 `permissions` → 直接用（旧签发路径，存量 token 2h 内自然淘汰）；
- 令牌含 `pv` 无 `permissions` → 走 resolver。
签发侧用 `fenglin.auth.jwt.include-permissions=true|false` 控制，先网关后签发，保证任何时刻两种令牌都能被正确处理。

## 6. 灰度与回滚

### 6.1 灰度步骤（按序，每步观察 ≥ 30min）

1. **准备**：`hub_user.permission_version` 迁移（默认 0）+ 索引无需新增；auth 部署内部接口（此时无人调用，安全）。
2. **网关先上（只增不改）**：网关升级到支持 `pv` + resolver，`permission-source=jwt`（行为与现状完全一致），观察 24h 无异常。
3. **小流量租户切换**：`permission-source=resolver` 仅对 1 个测试租户打开（用现有 `GrayGlobalFilter` 的租户/头匹配能力），auth 侧对该租户 `include-permissions=false`。
4. **扩量**：5% → 50% → 100% 租户，观察指标（见 §10）。
5. **收口**：全量后把 `include-permissions` 默认改为 `false`，保留 `jwt` 开关一个版本周期。
6. **清理**：下个版本删除 `permissions` claim 的签发分支与网关 `jwt` 兜底分支（避免"兼容代码永久化"）。

### 6.2 回滚

| 故障 | 回滚动作 | 预期恢复 |
|---|---|---|
| 权限解析 503 比例升高 | 网关 `permission-source=jwt` + auth `include-permissions=true`（双开关同时回切，滚动重启或配置中心下发） | ≤1 个滚动周期 |
| 权限错误（越权/漏权） | 同上回切；Redis 侧 `DEL fenglin:perm:*` 强制重算 | 立即 |
| Redis 不可用 | resolver 自动降级为"直连 auth 回源 + L1 短 TTL(10s)"，仍 fail-close 兜底；如 auth 也异常则回切 jwt | 立即 |
| pv 漂移（改权限不生效） | 提供 IAM 管理端"重算权限版本"运维接口（`POST /admin/users/{id}:refresh-permissions`） | 立即 |

> 回滚不需要回滚数据库：`permission_version` 列对旧代码无副作用。

## 7. 容量与性能估算

| 项 | 估算 | 依据 |
|---|---|---|
| 单用户权限串 | ~11 KB（管理员），普通员工 ~1–3 KB | 实测 456 条 / 11 182 字符 |
| L2 Redis 内存 | 活跃用户数 × 权限串 × 1.2；1 万活跃管理员 ≈ 130 MB；混合角色按 30% ⇒ ~40–60 MB | TTL 10min，只缓存活跃用户 |
| L1 Caffeine | 50k 条 × ~11 KB ≈ 550 MB 上限（需按实际内存下调到 10k 条 ≈ 110 MB） | 建议 `maximumWeight` + `weigher` 按权限条数计权 |
| auth 回源 QPS | 总读 QPS × miss 率（60s TTL 下稳定态 < 5%） | 登录预热后进一步下降 |
| 网关 P99 增量 | L1 命中 ≈ 0；L2 命中 ≈ +1–2ms；回源 ≈ +5–15ms | 内网 RPC |
| 令牌体积 | 16.6 KB → ≤1.1 KB（-94%） | 去掉 11 KB permissions |

> 落实时需按真实在线用户数复核 L1 容量；管理员权限串较大，建议 L1 对"权限条数 > 300"的用户只走 L2，避免单机内存被少数大权限用户占满。

## 8. 风险与缓解

| 编号 | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | Redis 成为新单点 | 权限解析 503 | L1 60s 保底；Redis 故障降级直连 auth；双开关回切 jwt |
| R2 | 网关与 auth 的 `pv` 语义不一致 | 权限错误 | 响应回传权威 `pv`，网关以响应为准覆盖缓存键 |
| R3 | 大权限用户（456+ 条）占满 L1 | 内存抖动 | 按权重限容 + 大权限用户仅走 L2 |
| R4 | 角色权限变更需要批量 `UPDATE` 用户版本 | 写放大（租户万级用户） | 先按用户级版本；规模上来后改为角色级版本 + 用户级增量位 |
| R5 | `roles` claim 首次真正签发 | 网关/审计若依赖则需联调 | 灰度期 `roles` 只增不改；下游不读 roles，无破坏 |
| R6 | 内部接口无鉴权被外部访问 | 信息泄露 | 与现有 `/internal/v1/**` 一致：仅内网暴露，网关路由不转发 `/internal/`（需在 §10 验收项确认现状确实未转发） |
| R7 | 生产入口 64KB 上限 | 灰度期旧令牌仍 28 KB | 本方案上线前继续保留 64KB 止血 + PLAT-11 入口层配置 |

## 9. 验收标准

1. 管理员 access token ≤ 1.5 KB；`Authorization + X-Permissions` ≤ 8 KB（可在默认 Nginx 配置下通过）。
2. 权限变更（角色权限点增删）后 ≤ 60s 在业务接口生效；撤销令牌仍即时生效（≤ 撤销缓存 TTL 30s）。
3. 21 个服务全部以新令牌直连 + 经网关访问均 200，无 400/431。
4. auth 回源 QPS 占网关总 QPS < 5%（稳定态）。
5. 回切开关演练：从 100% resolver 回切 jwt，5 分钟内全站恢复正常。
6. 观测项：`gateway_perm_cache_l1_hit / l2_hit / miss`、`gateway_perm_resolve_fail_total`、`auth_internal_permission_qps`、`gateway_request_header_bytes` 分位。
