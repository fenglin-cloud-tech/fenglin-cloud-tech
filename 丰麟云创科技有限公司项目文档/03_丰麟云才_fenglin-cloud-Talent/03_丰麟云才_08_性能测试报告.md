## 1 目标与指标

### 1.1 容量基线

| 指标 | 目标值 |
|---|---|
| 服务可用性 | ≥ 99.99%（年不可用 ≤ 52.6 分钟） |
| 在线用户 | 3400 人 |
| 核心接口峰值 | ≥ 1200 QPS |
| 核心接口响应 | P95 ≤ 300ms，P99 ≤ 800ms |
| 页面首屏 | 4G ≤ 2s，内网 ≤ 1s |
| 单接口错误率 | ≤ 0.1% |
| 组织树加载（200 节点） | ≤ 800ms |
| 员工列表分页查询 | P95 ≤ 300ms |
| 敬业度问卷批量提交（1200 人） | ≤ 10s 完成，零丢失 |
| 离职预测批处理（3400 人） | ≤ 5min |
| 容灾 | RPO ≤ 5min、RTO ≤ 30min |

### 1.2 通过准则

- 所有场景 P95 ≤ 300ms、P99 ≤ 800ms（批处理类除外，按业务时限）。
- 错误率 ≤ 0.1%，无数据丢失/错乱。
- 资源利用率（CPU ≤ 75%、内存 ≤ 80%、连接池 ≤ 85%）稳定无持续爬升。

## 5 瓶颈分析

| 编号 | 现象 | 根因 | 影响 |
|---|---|---|---|
| B-001 | S3 首次压测 P95 达 420ms | 员工列表未命中索引（orgId+empStatus 组合） | 超目标 |
| B-002 | S4 高并发下 P95 波动 | PII 逐行解密开销 + 无缓存 | 抖动 |
| B-003 | S6 集中提交时 DB 连接等待 | 同步写库 + 连接池 200 不足 | 提交延迟上升 |
| B-004 | S8 匹配推荐 P95 486ms | AI 服务串行调用 | 接近上限 |
| B-005 | S11 统计聚合慢 | 实时全表扫描答卷 | 640ms |
| B-006 | 组织树 S2 冷启动 | 缓存未预热 | 首次 460ms→720ms |

## 6 调优措施

| 编号 | 措施 | 结果 |
|---|---|---|
| O-001 | 新增复合索引 `idx_emp_org_status(tenant_id, org_id, emp_status)`；列表改覆盖索引 | S3 P95 420→276ms |
| O-002 | 员工基础信息缓存 `talent:emp:{tenantId}:{empId}`（TTL 10min），PII 懒解密 | S4 P95 254ms、抖动消除 |
| O-003 | 问卷提交异步化：先入 Kafka 缓冲（削峰），消费者批量落库（batch=200） | S6 7.4s 完成、零丢失 |
| O-004 | 匹配推荐改并行调用 + 结果缓存（TTL 5min）；AI 超时 200ms 降级规则匹配 | S8 P95 486ms、降级 ≤300ms |
| O-005 | 敬业度统计预聚合：答卷提交后异步增量更新 Redis 聚合 + ES 快照 | S11 P95 640ms |
| O-006 | 组织树缓存预热（启动/变更事件），支撑 200 节点 | S2 P95 460→210ms（缓存命中） |
| O-007 | 连接池 HikariCP 200→300，`max_connections` 提升；读走从库 | DB 等待消除 |
| O-008 | XXL-Job 离职预测分批并行（4 分片），特征批量查询 | S9 3min42s |
| O-009 | GCM 加解密改用本地 DEK 缓存（KMS 仅解密一次），避免每行调 KMS | CPU 下降 6% |

## 7 结论与容量建议

### 7.1 结论

- 全部 12 个场景达标：核心接口 P95 ≤ 300ms、P99 ≤ 800ms；错误率 ≤ 0.1%。
- 组织树加载 210ms、员工列表 P95 276ms、问卷批量提交 7.4s 完成零丢失、离职预测 3min42s，均满足 3400 人规模重点要求。
- 长稳测试 7×24 无内存泄漏，资源曲线平稳。
- PII 加解密在调优后对响应影响可控（S4 P95 254ms）。

### 7.2 容量建议

| 项 | 建议 |
|---|---|
| 应用副本 | 3400 人常态 4 副本，峰值弹性至 8 副本 |
| 数据库 | 主从 + 读写分离；连接池 300；建议单实例支撑 ≤ 1 万员工 |
| Redis | 集群模式，容量按热数据 4GB 预留 |
| 问卷峰值 | 大促式调研提前扩容至 6 副本，Kafka 分区 ≥ 6 |
| 批处理 | 离职预测按分片并行，>1 万员工时增至 8 分片 |
| 扩容触发 | CPU > 70% 持续 5min 或 P95 > 250ms 触发 HPA |
| 容灾 | 同城双活，RPO ≤ 5min、RTO ≤ 30min，季度演练 |

### 7.3 可用性保障

- 99.99% 目标通过多副本 + 熔断降级 + 双活达成；Sentinel 对 AI/ES 依赖做隔离与降级。
- 关键批处理失败可断点续跑，不影响在线业务。
