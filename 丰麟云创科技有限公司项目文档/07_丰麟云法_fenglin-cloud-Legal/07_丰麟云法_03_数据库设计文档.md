## 1 设计原则

1. **多租户**：所有业务表含 `tenant_id`，启用 PostgreSQL RLS 行级安全，跨租户访问默认拒绝。
2. **公共字段强制**：每表含 `id / tenant_id / created_by / created_at / updated_by / updated_at / deleted / version`。
3. **主键**：高并发写使用雪花 ID（`bigint`）；对外暴露资源标识同时以 `uuid` 列保证不可枚举。
4. **命名**：表名小写下划线、模块前缀 `legal_`；字段小写下划线。
5. **敏感字段加密**：PII（签署人手机号/身份证号、相对方联系人手机号）AES-256-GCM，配套 `{field}_hash`（SHA-256+租户盐）用于唯一性与检索，禁止明文列唯一索引。
6. **逻辑删除**：`deleted`（0 正常/1 删除），唯一约束以"未删除"为条件（部分索引）。**用印记录、签署记录、存证记录、DLP 审计日志不允许逻辑删除**（应用侧无删除接口，`deleted` 恒为 0）。
7. **乐观锁**：`version` 由 MyBatis-Plus `@Version` 维护。
8. **迁移**：所有 DDL/DML 通过 Flyway 脚本 `V1_0_x__*.sql` 提交，禁止手工改库。
9. **金额**：统一 `numeric(18,2)`；比例 `numeric(8,4)`；时间 `timestamptz`（UTC）。
10. **防篡改**：合同正文/条款快照、签署证据、用印记录、DLP 审计日志采用哈希链字段（`prev_hash`、`block_hash`、`chain_id`、`seq_no`）并与 WORM 存储同步。
11. **大表**：`legal_dlp_event`、`legal_dlp_audit_log`、`legal_sign_record` 按 `tenant_id` + 时间做声明式分区；ES 承担检索分流。

## 2 逻辑模型（ER）

```
┌───────────────────────────┐
│ legal_contract_template   │ 1:N ┌──────────────────────────┐
│ (模板)                     │────▶│ legal_template_version   │
└───────────┬───────────────┘     └───────────┬──────────────┘
            │ 1:N                             │ 1:N
            ▼                                 ▼
┌───────────────────────────┐     ┌──────────────────────────┐
│ legal_template_variable   │     │ (版本正文/变量默认值)      │
└───────────────────────────┘     └──────────────────────────┘

┌───────────────┐  1:N  ┌──────────────────────┐  1:N  ┌───────────────────┐
│ legal_contract│──────▶│ legal_contract_version│─────▶│ legal_contract_clause
│ (合同主表)     │       └──────────────────────┘       └───────────────────┘
└───┬───┬───┬───┘
    │   │   │ 1:N
    │   │   ├────────────────▶ legal_contract_party（相对方）
    │   │   ├────────────────▶ legal_signatory（签署方）
    │   │   ├────────────────▶ legal_approval_record（审批记录）
    │   │   ├────────────────▶ legal_performance_node（履约节点）
    │   │   ├────────────────▶ legal_expiry_reminder（到期提醒）
    │   │   └────────────────▶ legal_contract_attachment（合同附件）
    │   │ 1:1~1:N
    │   ├────────────────────▶ legal_seal_application ──▶ legal_seal_record
    │   │                                                 │
    │   │                        legal_seal（印章）◀──────┘
    │   └────────────────────▶ legal_sign_record ──▶ legal_evidence（存证）
    │                                                     │
    └────────────── 哈希链 ────▶ （integrity: prev_hash/block_hash 串联）

┌───────────────────┐  1:N  ┌──────────────────────┐
│ legal_sensitive_rule│────▶│ legal_dlp_policy      │
│ (敏感规则)          │      │ (策略，含通道与动作)   │
└───────────────────┘      └──────────┬───────────┘
                                       │ 1:N
                       ┌───────────────▼──────────────┐
                       │ legal_dlp_channel（通道配置） │
                       └──────────────────────────────┘

legal_dlp_event（外发/泄漏事件）1:N legal_dlp_event_handle（处置）
legal_dlp_event 1:N legal_watermark_record（水印施加/溯源）
legal_dlp_event ── 写 ──▶ legal_dlp_audit_log（审计，哈希链 + WORM）
legal_dlp_whitelist（例外）· legal_dlp_terminal（终端）

通用：legal_attachment（多态附件，object_type/object_id）
```

关系说明：

- `legal_contract_template` 1:N `legal_template_version` 1:N `legal_template_variable`；合同起草引用某个模板版本；
- `legal_contract` 1:N 版本/条款/相对方/签署方/审批记录/履约节点/到期提醒/附件/用印申请/签署记录；
- `legal_sign_record` 1:N `legal_evidence`（每份签署证据固化一条存证）；
- `legal_dlp_policy` 1:N `legal_dlp_channel`；`legal_sensitive_rule` 与 `legal_dlp_policy` 多对多（通过 `policy.rule_ids` JSONB 引用，避免中间表膨胀）；
- `legal_attachment` 以 `object_type` + `object_id` 多态关联合同/模板/事件等对象。

## 5 索引设计

### 5.1 主键与外键索引

- 所有表主键 `id`（雪花，`bigserial`/`bigint`）自动建 B-tree 主键索引；
- 所有 `*_id` 外键列建普通索引（用于关联查询）；
- `uuid` 列建唯一索引用于对外暴露。

### 5.2 关键业务索引

| 表 | 索引名 | 列 | 类型 | 说明 |
|---|---|---|---|---|
| `legal_contract` | `uk_contract_no` | `(tenant_id, contract_no)` | UNIQUE | 合同号唯一 |
| `legal_contract` | `idx_contract_status` | `(tenant_id, org_id, status, deleted)` | B-tree | 台账/审批队列 |
| `legal_contract` | `idx_contract_end` | `(tenant_id, end_date) WHERE deleted=0` | 部分索引 | 到期扫描 |
| `legal_contract` | `idx_contract_party` | `(tenant_id, party_b_id)` | B-tree | 按相对方查询 |

## 6 约束与 RLS

### 6.1 通用 RLS 策略

```sql
-- 为每张业务表启用 RLS 并创建租户隔离策略
ALTER TABLE legal_contract ENABLE ROW LEVEL SECURITY;
ALTER TABLE legal_contract FORCE ROW LEVEL SECURITY;
CREATE POLICY p_legal_contract_tenant ON legal_contract
  USING (tenant_id = current_setting('app.tenant_id')::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);
```

平台运营端（`platform:*`）跨租户访问通过独立数据库角色 `legal_platform_ro` 绑定 `USING (true)` 策略，并强制审计；应用连接默认使用 `legal_app` 角色（受 RLS 约束）。全部 27 张表按同一模板创建策略（策略名 `p_legal_{table}_tenant`）。

```sql
-- 防删除触发器（示例）

BEGIN
  RAISE EXCEPTION 'immutable table: % cannot be deleted/soft-deleted', TG_TABLE_NAME;
END; $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_no_delete BEFORE DELETE OR UPDATE OF deleted ON legal_seal_record
  FOR EACH ROW WHEN (TG_OP = 'DELETE' OR NEW.deleted = 1) EXECUTE FUNCTION fl_block_delete();
```

## 7 敏感字段加密

### 7.1 加密范围

| 表 | 明文字段 | 密文列 | 哈希列 | 展示尾号 |
|---|---|---|---|---|
| `legal_signatory` | 身份证号 | `signer_id_no_enc` | `signer_id_hash` | — |
| `legal_signatory` | 手机号 | `signer_mobile_enc` | `signer_mobile_hash` | `signer_mobile_tail` |
| `legal_contract_party` | 联系人手机号 | `contact_mobile_enc` | `contact_mobile_hash` | `contact_mobile_tail` |
| `legal_dlp_terminal` | MAC 地址 | — | `mac_hash` | — |

### 7.2 加密方案

- 算法：**AES-256-GCM**（随机 96-bit IV，随密文存储，含认证标签）；
- 密钥：由 KMS 托管，按租户派生数据密钥（DEK），主密钥（KEK）轮换 ≤ 90 天；
- 密文格式：`base64(iv || ciphertext || tag)`；
- 透明化：自定义 MyBatis `TypeHandler`（`AesGcmTypeHandler`）在读写时自动加解密，业务代码不感知。

### 7.3 检索与查询

- 哈希列算法：**SHA-256（`{field}` + 租户盐）**，租户盐存于 KMS；
- 精确检索走 `{field}_hash` 等值查询（如身份证查重、相对方 USCC 查重）；
- 禁止在明文列建唯一索引；唯一性约束建立在哈希列上（部分索引以 `deleted=0` 为条件）。

### 7.4 字段权限

- 展示层默认脱敏：手机号 `138****8888`、身份证 `110***********1234`、IP `10.*.*.*`；
- 查看明文需专用权限码（`legal:sign:pii:view`、`legal:party:pii:view`）且服务端记录审计；
- 签署证据中的签署人隐私信息在出证时按司法机关要求解密并留痕。
