## 1 部署架构

### 1.1 部署形态

| 形态 | 说明 | 隔离 |
|---|---|---|
| SaaS（默认） | 共享集群，按租户逻辑隔离（RLS） | `tenant_id` + RLS |
| 私有化 | 客户环境独立部署，命名空间 `fenglin-legal` | 独立库/独立集群 |

### 1.2 组件拓扑

| 组件 | 副本 | 资源 | 说明 |
|---|---|---|---|
| `fenglin-legal-service` | 6（生产建议 8–12） | 4C8G，JVM 4G（ZGC） | 无状态，HPA |
| `fenglin-gateway` | 2 | 4C8G | 鉴权/限流/路由 |
| PostgreSQL 15 | 1 主 2 从 | 16C64G，SSD | 流复制 + 自动故障转移 |
| Redis 7 Cluster | 3 主 3 从 | 4C16G | 缓存/锁/限流 |
| Kafka 3.6 | 3 Broker | 8C32G | 事件/上报削峰 |
| Elasticsearch 8 | 3 节点 | 8C32G | 检索 |
| MinIO | 4 节点 | 8C16G | 文件对象存储 |
| WORM 存储 | — | — | 防篡改一次性写入存储 |
| XXL-Job | 2 | 2C4G | 定时任务（到期提醒/归档/对账） |
| 监控栈 | — | — | Prometheus/Grafana/Loki/SkyWalking |

### 1.3 命名空间与域名

- 命名空间：`fenglin-legal`；
- 域名：`legal.fenglincloud.com`（Ingress + TLS 证书）；
- API 前缀：`/api/legal/v1`；前端：`/app/legal`（用户端）、`/admin/legal`（管理端）。

## 4 部署步骤

### 4.1 前置检查

```bash
# 1) 命名空间与配置
kubectl create namespace fenglin-legal --dry-run=client -o yaml | kubectl apply -f -
# 2) Secret 注入（从 KMS/Vault）
kubectl -n fenglin-legal get secret legal-secret   # 应存在
# 3) 中间件连通性
kubectl -n fenglin-legal run netcheck --rm -it --image=busybox -- \
  sh -c 'nc -z pg-primary 5432; nc -z redis-0 6379; nc -z kafka-0 9092'
```

### 4.2 数据库迁移（先于应用）

```bash
kubectl -n fenglin-legal create job --from=cronjob/legal-flyway-migrate legal-migrate-v1
kubectl -n fenglin-legal logs -f job/legal-migrate-v1   # 期望：Successfully applied 15 migrations
```

### 4.3 应用部署

```bash
# 应用清单：deployment + service + hpa + pdb + ingress
kubectl -n fenglin-legal apply -f deploy/legal-deployment.yaml
kubectl -n fenglin-legal apply -f deploy/legal-service.yaml
kubectl -n fenglin-legal apply -f deploy/legal-hpa.yaml
kubectl -n fenglin-legal apply -f deploy/legal-pdb.yaml
kubectl -n fenglin-legal apply -f deploy/legal-ingress.yaml

# 滚动发布
kubectl -n fenglin-legal rollout status deploy/legal-service --timeout=300s
```

### 4.4 部署清单（示例要点）

- `deployment`：`replicas: 8`、`readinessProbe: /actuator/health/readiness`、`livenessProbe: /actuator/health/liveness`、`resources.requests 2C4G / limits 4C8G`、`terminationGracePeriodSeconds: 60`；
- `hpa`：`minReplicas 6 / maxReplicas 16`，CPU 目标 65%；
- `pdb`：`minAvailable 4`（保障滚动更新与故障时可用）；
- `ingress`：`legal.fenglincloud.com`，TLS（cert-manager 签发），限流注解。

## 6 中台与 CA 集成配置

### 6.1 中台接入

| 集成 | 配置/操作 |
|---|---|
| 认证 | 注册 OAuth2 客户端（client_id/secret），配置回跳；启用二次认证 `step-up` 端点 |
| 权限 | 同步本品权限码字典（`legal:*`、`tenant:legal:*`）至 IAM |
| 工作流 | 导入 BPMN：`legalContractApproval`、`legalSealApproval`、`legalContractSign`、`legalDlpEventHandle`、`legalDlpReleaseApproval` |
| 消息 | 配置通知模板（到期提醒/签署邀请/拦截告警/放行结果） |
| 审计 | 配置审计通道与留存策略（合同与 DLP 12 个月） |
| 搜索 | 创建索引 `legal_contract_idx`、`legal_dlp_event_idx` 与 IK 分词 |

### 6.2 CA/电子签章服务配置（管理端）

1. 管理端 `PUT /api/legal/v1/admin/config/ca-provider` 配置服务商（endpoint、appId、secretRef、algorithm、priority）；
2. 连通性探测返回 `connectivity: OK`；
3. 配置回调地址白名单与验签密钥（`LEGAL_INTERNAL_SIGN_KEY`）；
4. 印章/证书在管理端维护并与服务商绑定（`certSerial`）；
5. 灰度：先启用 1 个服务商，签署验证通过后再启用多服务商与优先级。

### 6.3 DLP Agent 接入

1. Agent 通过 `POST /internal/dlp/terminals/register` 注册（携带注册令牌）；
2. 服务端返回 `policyVersion` 与心跳间隔；
3. Agent 周期性拉取策略（版本变化）与上报心跳；
4. 外发动作调用 `POST /internal/dlp/decide` 决策，事件上报 `/dlp/events/report`。

## 7 监控与告警

### 7.1 关键指标

| 指标 | 阈值 | 告警级别 |
|---|---|---|
| 接口 P95 | > 300ms 持续 5min | 警告 |
| 接口错误率 | > 0.5% 持续 5min | 严重 |
| 5xx 占比 | > 1% | 严重 |
| 服务副本可用 | < minReplicas | 严重 |
| 数据库连接池使用率 | > 85% | 警告 |
| DB 慢查询（>500ms） | > 10/min | 警告 |
| Kafka 消费延迟 | > 10s | 警告 |
| DLP 决策 P95 | > 300ms | 严重 |
| DLP 上报积压 | > 50000 | 警告 |
| 哈希链写入失败 | > 0 | 严重 |
| 完整性校验失败 | > 0 | 紧急 |
| CA 调用失败率 | > 5% | 严重 |
| 证书到期 | ≤ 30 天 | 警告 |
| 终端离线率 | > 10% | 警告 |

### 7.2 监控栈

- 指标：Prometheus + Grafana（含业务看板：合同、签署、DLP）；
- 日志：Loki（结构化 JSON，含 `requestId`/`tenantId`）；
- 链路：SkyWalking（跨服务追踪）；
- 告警：Alertmanager → 站内信/邮件/企微飞书钉钉；紧急告警电话。

### 7.3 巡检项（每日/每周）

- 每日：健康检查、错误日志、Kafka 积压、哈希链校验、CA 连通性、证书到期；
- 每周：慢查询、容量趋势、终端在线率、DLP 误报率、备份完整性。

## 8 备份与恢复

### 8.1 备份策略

| 对象 | 方式 | 频率 | 保留 |
|---|---|---|---|
| PostgreSQL | 全量 `pg_basebackup` + WAL 归档 | 全量每日，WAL 持续 | 全量 30 天，WAL 7 天 |
| MinIO | 跨站点复制 | 持续 | 按生命周期 |
| WORM | 异地冗余复制 | 持续 | 长期（不删除） |
| Redis | RDB/AOF | 每小时 | 7 天 |
| ES | 快照 | 每日 | 14 天 |
| 配置/Secret | 配置库版本化 | 变更即备份 | 长期 |

### 8.2 恢复演练（季度）

| 场景 | 步骤 | 目标 |
|---|---|---|
| 单表误删 | 从备份/归档恢复表 | ≤ 1h |
| 主库故障 | 提升从库为主 | RTO ≤ 30min，RPO ≤ 5min |
| 站点故障 | 切换同城双活 | RTO ≤ 30min |
| 存证/审计恢复 | 从 WORM 恢复并校验链 | 链完整 |

### 8.3 校验

恢复后必须执行：哈希链完整性校验（`/internal/evidence/chain-verify`、`/dlp/audit-logs/verify`）、存证核验抽样、RLS 生效核查。

## 9 扩容、发布与回滚

### 9.1 扩容

- 应用：HPA 自动（CPU 65%）或手动 `kubectl scale`；每 +4 副本约 +600 QPS；
- 数据库：读扩展（从库分流）、连接池调整；写瓶颈考虑升配；
- Kafka：增加分区 + 消费者；ES：增加节点与分片副本。

### 9.2 发布

- 滚动发布（`maxSurge 25% / maxUnavailable 0`）+ PDB 保障；
- 数据库迁移先行且向后兼容（先加列后用列）；
- 灰度：按租户/流量比例灰度，观察指标与错误率；
- 变更窗口：避开月末集中签署期。

### 9.3 回滚

| 场景 | 回滚方式 |
|---|---|
| 应用异常 | `kubectl rollout undo deploy/legal-service` |
| 迁移异常 | 停止发布，按快照恢复；禁止手工改库 |
| 数据异常 | 从备份点恢复（PITR） |

## 10 常见故障排查

| 现象 | 可能原因 | 排查与处理 |
|---|---|---|
| 接口 401/403 | 令牌失效/端别不符/权限缺失 | 检查令牌 `client_type` 与 `X-Client-Type`；核对权限码 |
| 合同提交审批失败 `7001004` | 必填变量缺失 | 检查模板变量配置与合同变量快照 |
| 用印失败 `7001006` | 印章停用/证书过期 | 管理端核查印章状态与证书有效期 |
| 用印失败 `7001007` | 版本不一致 | 比对用印版本与审批版本 |
| 签署失败 `7001008` | CA 服务不可用 | 检查 CA 连通性与限流；任务自动重试，超限人工 |
| 签署证据校验失败 `7001009` | 证据缺失/验签失败 | 检查回调日志与时间戳服务；核对 `doc_hash` |
| 完整性告警 `legal.integrity.alert` | 数据被篡改/链断裂 | 冻结对象，比对 WORM，人工核查，启动应急 |
| DLP 决策延迟高 | 缓存未命中/策略过多 | 检查策略预热与规则数量；扩容决策实例 |
| DLP 事件积压 | 上报激增/消费不足 | 提升分区与消费者，批量落库 |
| 到期提醒未触达 | 任务未执行/消息失败 | 检查 XXL-Job 执行记录与消息通道；重试补偿 |
| 检索结果滞后 | ES 索引延迟 | 检查事件消费与对账任务；必要时回源查询 |
| 报表超时 | 聚合查询重 | 检查预聚合与物化视图，走缓存 |

常用命令：

```bash
# 查看 pod 与事件
kubectl -n fenglin-legal get pods -o wide
kubectl -n fenglin-legal describe pod <pod>
# 日志（含 requestId 过滤）
kubectl -n fenglin-legal logs deploy/legal-service --tail=500 | findstr "<requestId>"
# 健康与指标
kubectl -n fenglin-legal exec deploy/legal-service -- wget -qO- localhost:8081/actuator/health
# Kafka 消费延迟
kafka-consumer-groups --bootstrap-server kafka-0:9092 --describe --group legal-event-consumer
```

## 11 应急预案

| 级别 | 场景 | 处置 |
|---|---|---|
| P0 | 服务整体不可用 / 完整性告警 | 启动应急，切换双活，冻结受影响对象，通知安全负责人，2h 内出初步结论 |
| P0 | 数据篡改 | 冻结对象，WORM 取证，恢复可信快照，追溯操作审计，法务介入 |
| P1 | CA 服务大面积不可用 | 签署排队重试 + 切换备用 CA，公告用户，监控恢复 |
| P1 | DLP 拦截失效 | 立即按默认策略阻断敏感通道，排查决策链路，恢复后复盘 |
| P1 | 数据库主库故障 | 触发故障转移，验证数据一致性，恢复后校验哈希链 |
| P2 | 性能劣化 | 扩容 + 限流 + 降级（AI/ES），定位瓶颈 |

应急联系与升级路径：值班工程师 → 平台运维负责人 → 安全合规组 → 产品负责人；重大事件同步客户与法务。
